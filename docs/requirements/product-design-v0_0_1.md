# alphaloop 产品设计文档

**日期：** 2026-08-24
**类型：** 产品设计（Product Design）
**上游依据：** `docs/requirements/product-positioning-requirements.md`

## 0. 这份文档是什么，不是什么

这是**产品设计文档**，不是定位文档。

| | 定位文档（上游） | 本设计文档 |
| --- | --- | --- |
| 回答 | 为什么存在、给谁、边界在哪 | 有哪些功能、长什么样、怎么走完一遍 |
| 产出 | 品类、目标用户、成功标准、架构边界、安全语义 | 功能地图、逐功能规格、状态机、主流程与异常流程、文案规则 |
| 变更方式 | 定位变了才改 | 功能取舍变了就改 |

本文档**继承而不重述**上游定位文档的以下结论，并把它们当作不可协商的约束：

- 三结论语义 `FOUND` / `NO_EVIDENCE` / `INCONCLUSIVE`（上游 §1、§6.3）。
- 证据权威：只有确定性硬门槛评估器能产出 `FOUND`；界面、报告、LLM 都不能覆盖门槛（上游 §9.3）。
- 交易硬墙：不持有券商凭据、不下单、不自动晋级（上游 §9.4）。
- 本机优先、Web 控制台为主要长任务界面、CLI 与 Agent Skill 为次要入口（上游 §10）。
- 一次隔夜运行内绝不静默执行新的经济假设（上游 §4.3、§6.1）。

**本文档新增的产品决策**（上游未定义，需在本轮评审确认）集中在一条主线上，正文中以「**新增**」标注：

1. **验证方法配置**（§3.4）：开始研究时用户可查看、选择、调整本轮跑哪些验证点，区分硬门槛与诊断项，随协议一起冻结。
2. **验证进度**（§3.10）：运行中逐验证点可见 `pending` / `running` / `pass` / `fail` / `skipped`，并明确 `skipped` 的结论语义。
3. **策略验证结果**（§3.13）：每个入围与淘汰候选按同一份清单逐条展示结果，并可下钻到证据。

三者是同一件事的三个时相——冻结前选、运行中看、结束后读——共用同一套验证点标识符、分组与释义。

**叙事标签不是功能名。** 现有控制台的阶段导航 `Before bed` / `Morning` / `Help` 是叙事外壳，且其标签与配色已被 e2e 锁定（见
`docs/requirements/2026-08-21-futuristic-console.md` 的 Implementation locks），本文档**不要求改名**。但功能单元一律以能力命名（如「验证方法配置」「候选漏斗」），阶段只是这些能力的摆放位置。§2.3 给出能力到阶段的映射。

## 1. 一句话与产品亮点

### 1.1 一句话

> alphaloop 是跑在你自己机器上的隔夜量化研究实验室：冻结一个可检验的经济假设，让它在无人值守的夜里按预先声明的验证清单跑完，第二天给你一个可审计、可复现、敢于说「没有证据」的结论。

### 1.2 三个产品亮点

亮点不是「功能多」，而是三件别的工具不做的事。

**亮点一：结论可信（trustworthy conclusion）**

- 一次运行只给**一个**主结论：`FOUND` / `NO_EVIDENCE` / `INCONCLUSIVE`。
- `FOUND` 的唯一来源是确定性门槛评估器；证据缺一项就退化为 `INCONCLUSIVE`，绝不四舍五入成通过。
- 产品愿意输出坏消息。`NO_EVIDENCE` 是一等结论，有独立配色与独立文案，不是「失败」。
- 所有结论文案都自带反夸大声明：`FOUND` 不承诺 alpha，`NO_EVIDENCE` 也不承诺 alpha 不存在。

**亮点二：研究可审计（auditable research）**

- 验证清单在冻结时就固定，并被 `spec_id` 内容哈希覆盖；跑完之后无法追认「我本来就想跑这几项」。
- 每个候选、每次方法修订都进 trial ledger，并计入多重检验计数（`n_trials` 直接进入 DSR 去膨胀）。
- **放宽留痕**（**新增**）：任何相对市场档案默认验证清单的放宽（关掉一个门槛、把门槛降级成诊断），都会在冻结确认页、结论页和 `.asb` lineage 里留下标记。放宽是允许的，隐藏放宽是不允许的。
- 结论页每一行证据都能下钻到 `runs/<run_id>/evidence/` 里的原始输入；报告是证据的视图，不是证据的来源。

**亮点三：隔夜运行本机可恢复（local recoverable overnight runs）**

- 关掉浏览器、关掉提交用的终端，任务不停；这一点在预检时就明说。
- 挂起或关机会停止计算；这一点也在预检时就明说，而不是等用户第二天发现进度停在凌晨两点。
- checkpoint 让 worker 崩溃后从最近一个完整检查点续跑；恢复次数在任务卡上可见。
- 数据、代码、结论全部留在本机，不需要把策略或数据集交给第三方 SaaS。

### 1.3 三个恰到好处的惊喜时刻

克制使用，只在能增加信任的地方出现。

1. **冻结时的验证清单收束**：点「冻结并提交」前，用户看到一份「本轮将检验什么、总共会试多少组参数、哪些项可能因样本不足被跳过」的清单。这份清单在冻结的瞬间从「可编辑」变成「只读 + `spec_id`」——研究从此有了不可反悔的判决标准。
2. **早晨的唯一判决**：进入结论页，第一屏只有一个词和一句人话解释，其余全部往下沉。用户不需要在十二个图表里自己拼结论。
3. **诚实的跳过**：如果某个验证点因为样本不够没跑成，产品说「跳过 · 样本不足」并把结论降为 `INCONCLUSIVE`，而不是悄悄少算一项然后给 `FOUND`。

| 能力 | 位置 |
| --- | --- |
| F1 | 顶部 masthead 常驻仪表（`LOCAL` / worker / 主机 / 心跳） |

### 2.4 结论优先的信息层级

任务详情从上到下固定顺序，不允许因为某段内容长就上移：

```text
1  主结论（一个词）+ 一句解释
2  主要证据 + 停止原因
3  任务状态 / 心跳 / 恢复次数（与研究结论明确分开）
4  验证进度（运行中）或 验证清单结果（终态）
5  入围候选 + 每候选的策略验证结果
6  候选漏斗（淘汰主因）
7  方法修订
8  下一假设建议队列
9  试验台账
10 已封存报告 report.md 原文
```

## 3. 功能规格

每个功能按 **目标 / 入口 / 关键 UI 元素 / 状态 / 边界** 描述。

### 3.1 F1 本机启动与健康

**目标：** 让用户在三秒内确认「这台机器现在能不能接研究任务」。

**入口：** `alphaloop start`（可带 `--data-dir` / `--host` / `--port` / `--detach`），随后浏览器打开本机地址；控制台任何页面顶部常驻仪表。

**关键 UI 元素：**

| 元素 | 内容 | 说明 |
| --- | --- | --- |
| `LOCAL` 标记 | 静态 | 声明这是本机运行，数据不出机 |
| worker 标记 | `idle` 或 `N running` | 当前有几个 worker 在跑 |
| 主机标记 | `awake` | 提醒主机需保持唤醒 |
| 心跳标记 | `heartbeat` + 时间戳 | 仅当选中任务有心跳时出现 |
| 唤醒约束说明 | 固定句子 | 在 Help 与预检结果里各出现一次 |

**状态：**

| 状态 | 判定 | 界面表现 |
| --- | --- | --- |
| 未启动 | 页面无法加载 | 浏览器错误页；CLI 提示先 `alphaloop start` |
| 空闲可接单 | 健康检查通过、无 running 任务 | worker 标记 `idle` |
| 有任务在跑 | 有 running 任务 | worker 标记 `N running`，运行中脉冲动效 |
| 正在恢复 | 心跳超期或 worker 进程消失 | 任务卡显示恢复次数，任务保持 running |
| 恢复放弃 | 恢复次数达上限 | 任务转 `failed`，详情显示 worker 错误 |

**边界：** 健康只描述本机守护进程与 worker，不代表数据源可用性（那属于预检）。守护进程默认只绑本机回环地址；不在控制台里提供「暴露到局域网」的开关。

### 3.2 F2 研究任务列表

**目标：** 一屏扫完「有没有需要我处理的结论」，并能用键盘在任务间跳。

**入口：** Morning 阶段左栏，常驻；冻结提交后自动切到该阶段并定位到新任务。

**关键 UI 元素：** 每张任务卡包含

- `run_id`（等宽字体）
- 任务状态：`queued` / `running` / `completed` / `failed` / `cancelled`
- 研究结论：`FOUND` / `NO_EVIDENCE` / `INCONCLUSIVE` / `NONE`
- 冻结时的假设陈述（一行，超出截断）
- `n_trials` 与搜索进度条 `n_trials / planned_n_trials`
- 迷你漏斗条（通过 / 未通过 / 证据不完整三段）
- 验证清单摘要（**新增**）：`验证点 5 · 放宽 1`，放宽数 > 0 时高亮
- 恢复次数（仅 > 0 时出现）

**状态：**

| 状态 | 界面表现 |
| --- | --- |
| 空列表 | 空态引导：如何加载示例 → 预览 → 冻结提交，并附「不承诺 alpha」声明 |
| 加载中 | 保留上一次列表，不闪空 |
| 有任务 | 按创建时间倒序；running 任务带脉冲；failed 任务边框告警色 |
| 选中 | 卡片高亮，右侧渲染任务详情 |

**边界：** 列表不做搜索、标签、归档、批量操作。首版一人一机，任务量级不需要这些。不做跨市场档案的候选排名（上游 §5.5）。

### 3.3 F3 新建研究：假设与市场档案

**目标：** 一分钟内把一个可检验的经济假设变成结构化输入，靠**识别**而不是**回忆**——用户看到可选项，而不是背 YAML 键名。

**入口：** Before bed 阶段的引导表单；YAML 文本域作为等价的高级入口，两者双向同步。

**关键 UI 元素：**

| 分组 | 字段 | 控件 | 说明 |
| --- | --- | --- | --- |
| 假设 | 假设陈述 | 文本 | 一句可判真伪的话 |
| 假设 | 经济逻辑 | 文本 | 为什么应该成立 |
| 假设 | 信号机制 | 下拉（分组：趋势 / 均值回复 / 相对价值） | 受约束 DSL 的 `kind`，每项带 `id — 人话` 释义 |
| 市场 | 标的范围 | 文本 | 逗号分隔 |
| 市场 | 市场档案 | 下拉 | `us-equity-daily` / `crypto-daily`，带日历 / 成本 / 默认基准释义 |
| 市场 | 基准 | 文本 | 默认随市场档案填充 |
| 运行 | 随机种子 | 数字 | 复现所需 |
| 运行 | 时间预算（秒） | 数字 | |
| 运行 | 成本预算（USD） | 数字 | |
| 数据 | 数据集 id / sha256 | 文本 | 内容寻址快照 |
| 数据 | 上传 parquet / CSV | 文件 | 上传后自动回填 id 与 sha256 |

**关键设计约束：**

- 信号机制下拉只列**方向性信号**。波动率特征与需要成交量的信号不在列表里；若用户直接粘 YAML 绕过，预检拒绝并说明原因（例如「波动率特征不是方向性信号机制」）。
- 参数网格**不由用户填**。选定信号机制即确定该轮的方法参数网格与 `planned_n_trials`。这是反 p-hacking 的结构性选择：用户能选检验什么，不能一格一格地喂参数直到通过。
- 「加载示例」只填表单与 YAML，绝不创建任务、绝不产生 `FOUND`。

**状态：** 空表单 / 部分填写（冻结按钮保持禁用）/ 校验失败（行内错误 + 汇总错误区）/ 已预览且未改动（冻结按钮可用）/ 预览后被改动（冻结按钮重新禁用，提示需重新预览）。

**边界：** 不提供自然语言直出策略代码；不提供自由 Python；无法用当前 DSL 表达的假设在预检阶段被拒（上游 §8.2.1、§9.1）。

### 3.4 F4 验证方法配置（**新增**，核心）

**目标：** 让用户在研究开始前**看见并决定**「这一轮用什么标准判定成功」，并且这份决定与协议一起冻结、可审计、放宽留痕。

这是本设计文档相对上游定位文档最重要的功能增量。上游只说「预先声明的硬门槛」，没有说这份声明如何被人看见和调整。

#### 3.4.1 概念模型：验证点

**验证点（verification point）** 是本轮研究中一次可判定的检验。每个验证点有：

| 属性 | 取值 | 说明 |
| --- | --- | --- |
| `id` | 稳定标识符 | 如 `dsr`、`walk_forward`、`cpcv` |
| `class` | `hard_gate` / `diagnostic` | 是否参与 `FOUND` 判定 |
| `scope` | `gate` / `bound` / `run` | 顶层门槛 / 挂在某门槛下的子校验 / 全轮范围的硬校验 |
| `attaches_to` | 空 或 某个硬门槛 `id` | `bound` 必填；`run` 为空 |
| `enabled` | 是否本轮执行 | |
| `precondition` | 样本量 / 数据源要求 | 决定是否会被 `skipped` |
| `params` | 阈值等 | 首版多为固定常量，见 §3.4.2 |

`class` 只有两个取值，这两个取值的语义差别是产品的核心承诺：

- **硬门槛（hard_gate）**：全部到齐且全部通过 → `FOUND`。任一失败 → `NO_EVIDENCE`。任一缺席（含被跳过）→ `INCONCLUSIVE`。
- **诊断项（diagnostic）**：结果被记录、被展示、可下钻，但**永不**决定 `FOUND`，也**永不**阻止 `FOUND`。诊断项被跳过只是少一条信息。

`scope` 描述这个检验问的是哪一层的问题，它不改变 `class` 的语义——一个 `bound` 或 `run` 范围的检验若 `class` 为 `hard_gate`，它同样拥有否决权。

**绑定子校验（bound sub-check）** 是挂在某个硬门槛上的硬性检验，它自己不单独出现在结论行里，而是让父门槛的判定更严：父门槛必须自身通过**且**其启用的绑定子校验全部通过。这一层存在的原因是现实——walk-forward 的 regime 稳定性、多数 fold、CPCV 都不是独立结论，它们就是「OOS 是否站得住」的组成部分。界面上它们以缩进方式挂在父门槛下面，而不是平铺成一堆同级复选框。

**全轮硬校验（run-scope check）** 是对整轮而非某一门槛提问的硬性检验：净成本口径、嵌套留出、回测过拟合概率。它们不属于任何单一门槛，界面上单独成一组显示在顶层门槛之后。记账上它们的结果会被附在本轮启用的第一个硬门槛上（按门槛优先序），这是产物布局的实现细节，界面不应把这个归属当作语义呈现。

#### 3.4.2 验证点登记表（首版）

**硬门槛（顶层，六项）**

| id | 释义 | 判定 | 前置条件 | `us-equity-daily` 默认 | `crypto-daily` 默认 |
| --- | --- | --- | --- | --- | --- |
| `dsr` | Deflated Sharpe Ratio | 按 `n_trials` 去膨胀后 DSR ≥ 0.95 | 收益观测 ≥ 30 | 开 | 开 |
| `walk_forward` | walk-forward OOS | OOS 平均 Sharpe > 0 | 样本足够切出训练 / 测试 / 禁运窗口 | 开 | 开 |
| `vs_random` | versus random | 最大回撤优于块自举随机基线的中位数（200 次模拟，块长 21） | 无额外要求 | 关 | 关 |
| `vs_buy_hold` | versus buy-and-hold | Sharpe > 标的买入持有 | 重叠观测 ≥ 5 | 关 | **开** |
| `vs_benchmark` | versus benchmark | Sharpe > 基准买入持有 | 基准序列可用 | 开 | 开 |
| `data_consistency` | data consistency | 跨源收盘价平均相对误差 ≤ 5%、p95 ≤ 20%、收益相关性 ≥ 0.95 | **需第二数据源** | 关 | 关 |

**绑定子校验（挂在 `walk_forward` 下，硬性）**

| id | 释义 | 判定 | 前置条件 | 默认 |
| --- | --- | --- | --- | --- |
| `regime_stability` | 两段 regime 稳定 | OOS 前后半段 Sharpe 均 > 0 | OOS 观测 ≥ 30 | 开 |
| `median_fold` | 中位 fold | 各 fold Sharpe 的中位数 > 0 | fold 数 ≥ 3 | 开 |
| `majority_folds` | 多数 fold | 严格多数 fold 的 Sharpe > 0 | fold 数 ≥ 3 | 开 |
| `cpcv` | 组合式净化交叉验证 | 路径 Sharpe 的均值与中位数 > 0，且多数路径 > 0 | 分组后每组 ≥ 20 观测 | 开 |

`walk_forward` 未启用时整组随之隐藏，因为它们检验的正是 walk-forward 的 OOS 结果。

**全轮硬校验（对整轮提问，硬性）**

| id | 释义 | 判定 | 前置条件 | 默认 |
| --- | --- | --- | --- | --- |
| `net_of_cost` | 净成本收益 | 所有收益按市场档案的 `cost_bps` × 换手扣费后再计 | 无 | **强制开，不可关** |
| `nested_holdout` | 嵌套留出 | 锁定尾段 Sharpe > 0 | 内层前缀 ≥ 120 观测，留出段 ≥ 30 观测 | 开 |
| `pbo` | 回测过拟合概率 | PBO < 0.5 | 至少 2 条试验收益序列 | 开 |

`net_of_cost` 是所有门槛的公共口径而不是可选检验：不扣成本的 Sharpe 不值得判定。`pbo` 在结论生成时刻计算，因此它是唯一能把已经算出的 `FOUND` 降级为 `NO_EVIDENCE` 的验证点。

**诊断项**

| id | 释义 | 判定 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `llm_judge` | 报告质量评审 | 可读性 / 决策质量 / 风险披露 三项均 ≥ 7 | 关 | 契约层已禁止它成为硬门槛，界面上也不提供升级选项 |

默认的诊断层只有一项，这是刻意的。它的作用是给「有价值但不该有否决权」的检查一个明确落位，而不是先把层级填满。`vs_random`、`vs_buy_hold`、`pbo` 可以由用户降级为诊断（见 §3.4.4），降级后即出现在诊断层，并计入放宽留痕。

#### 3.4.3 默认从哪来

默认验证清单 = **市场档案默认** ⊕ **协议模板默认**：

- **市场档案默认**给出该市场必须回答的问题。`crypto-daily` 默认多一项 `vs_buy_hold`，因为在加密市场里「买入并持有标的本身」是极强基线，不显式对比很容易把 beta 当成 alpha。`us-equity-daily` 不默认开它，因为 `vs_benchmark`（对 SPY）已经承担了同类角色。
- **协议模板默认**由信号机制决定绑定子校验是否有意义。例如 `pairs_spread` 的成型窗口较长，`nested_holdout` 的样本压力更大，模板会在配置页直接标出「可能跳过」。
- 冲突时以市场档案为准，并在配置页显示来源标签 `来自市场档案` / `来自协议模板`。
- `data_consistency` 两个档案都默认关闭：首版数据快照通常是单源，默认开会让绝大多数运行直接 `NO_EVIDENCE`（缺第二数据源判为失败），这是误导。想跑它的用户必须先准备第二数据源，配置页会说明这一点。

#### 3.4.4 用户能改什么，不能改什么

| 操作 | 允许 | 规则 |
| --- | --- | --- |
| 关闭一个硬门槛 | 是 | 至少保留一个硬门槛；`dsr` 与 `walk_forward` 至少保留其一为硬门槛 |
| 开启一个默认关闭的硬门槛 | 是 | 前置条件不满足时给出「必定跳过」预判 |
| 把 `vs_random` / `vs_buy_hold` / `pbo` 降级为诊断 | 是 | 计入放宽留痕 |
| 把 `llm_judge` 升级为硬门槛 | 否 | 契约层禁止；控件呈禁用态并给出原因 |
| 关闭 `net_of_cost` | 否 | 成本是结构性前置，不是可选项 |
| 关闭 `walk_forward` 的绑定子校验 | 是（逐项） | 计入放宽留痕；`walk_forward` 本身关闭时整组随之隐藏 |
| 关闭 `nested_holdout` | 是 | 计入放宽留痕 |
| 改阈值（DSR 置信度、PBO 上限等） | 否 | 首版阈值为固定常量。放开阈值等于放开「调到通过为止」的后门 |
| 冻结后修改任何一项 | 否 | 属于经济性修订，进人工审核队列，需新 `spec_id` |
| 覆盖已产出的门槛结果 | 否 | 界面不存在任何 override 控件（已被测试锁定） |

**放宽留痕（relaxation trail）**

放宽 = 相对市场档案默认清单的任何削弱：关掉硬门槛、把硬门槛或全轮硬校验降级为诊断、关掉绑定子校验或全轮硬校验。

- 配置页实时显示 `放宽 N 项`，并列出每一项与原因输入框（原因可空，但空原因也会被记录为空）。
- 冻结确认页把放宽项单独成块，不与其它清单项混排。
- 结论页在主结论下方显示 `本轮放宽 N 项` 徽标，点击展开清单。
- `.asb` 的 lineage 记录放宽清单。导出到 AlphaStrategy 的候选包，自带「这个结论是在什么标准下得到的」。

**收紧不需要留痕**，因为它不会让结论变得更好看。

#### 3.4.5 关键 UI 元素

配置页是 Before bed 流程的一节（在假设与市场之后、预检之前），默认折叠为一行摘要，展开后是分组清单：

```text
验证方法          硬门槛 3 · 全轮硬校验 2 · 诊断 1 · 放宽 1 · 预计 9 组参数

硬门槛（决定 FOUND）
  [x] dsr — Deflated Sharpe Ratio                    来自市场档案
      按 9 组试验去膨胀后需 DSR ≥ 0.95 · 需 ≥30 个收益观测
  [x] walk_forward — walk-forward OOS                来自市场档案
      OOS 平均 Sharpe 需 > 0
      [x] regime_stability  两段 regime 均需 > 0
      [x] median_fold       中位 fold 需 > 0
      [x] majority_folds    多数 fold 需 > 0
      [x] cpcv              路径 Sharpe 均值与中位需 > 0     可能跳过：分组样本偏少
  [x] vs_benchmark — versus benchmark                来自市场档案
  [ ] vs_random — versus random
  [ ] vs_buy_hold — versus buy-and-hold
  [ ] data_consistency — data consistency            必定跳过：未提供第二数据源

全轮硬校验
  [x] net_of_cost — 净成本收益                        强制启用，不可关闭
      所有收益按 5 bps × 换手扣费后计算
  [x] nested_holdout — 嵌套留出                       来自协议模板
      锁定尾段 Sharpe 需 > 0 · 需内层 ≥120 观测

诊断项（不决定 FOUND）
  [x] pbo — 回测过拟合概率                            放宽：由全轮硬校验降级
      结果会展示，但不会阻止 FOUND
  [ ] llm_judge — 报告质量评审                        不可作为硬门槛
```

必备元素：

1. **分组清单**：硬门槛组（绑定子校验缩进在父门槛下）、全轮硬校验组、诊断项组，三组视觉层级明确不同，且 F4、F10、F13 三处的分组与顺序完全一致。
2. **每项一行释义**：`id — 人话`，第二行是判定条件与前置条件，用户不需要查文档。
3. **来源标签**：`来自市场档案` / `来自协议模板`，让用户知道默认不是随机的。
4. **可行性预判徽标**（见 §3.4.6）：`可执行` / `可能跳过：<原因>` / `必定跳过：<原因>`。
5. **类别切换控件**：允许降级的项上出现「作为诊断运行」切换；不允许的呈禁用态并给出原因。
6. **放宽计数与清单**：始终可见，不藏在折叠里。
7. **`planned_n_trials` 联动**：清单变化不改变参数网格，但 DSR 的去膨胀强度取决于 `n_trials`，配置页要说明这层联系。
8. **恢复默认**按钮：一键回到当前市场档案的默认清单。

#### 3.4.6 可行性预判

配置页与预检共用一套判定，在**冻结之前**就告诉用户哪些验证点跑不成。输入是数据快照长度、市场档案的年化周期数、信号机制的成型窗口；输出三档：

| 预判 | 判定依据 | 界面 |
| --- | --- | --- |
| `可执行` | 前置条件按当前快照可满足 | 无徽标 |
| `可能跳过` | 处在边界（例如 CPCV 分组后每组接近 20 观测下限） | 中性徽标 + 原因 |
| `必定跳过` | 前置条件确定无法满足（例如无第二数据源、内层前缀 < 120 观测） | 告警徽标 + 原因 |

**这是本功能最重要的产品价值**：让「样本不够」在睡前暴露，而不是第二天以 `INCONCLUSIVE` 的形式暴露。若清单里存在 `必定跳过` 的**硬门槛**，冻结确认页必须以显著方式提示「按当前清单，本轮最好的结果是 `INCONCLUSIVE`」，用户仍可坚持冻结（研究者有权跑一次探路），但不能声称不知情。

#### 3.4.7 状态

| 状态 | 界面表现 |
| --- | --- |
| 未展开 | 一行摘要：硬门槛数 · 全轮硬校验数 · 诊断数 · 放宽数 · 预计参数组数 |
| 编辑中 | 清单可勾选；冻结按钮禁用（任何编辑都要求重新预检） |
| 违反约束 | 行内错误：`至少保留一个硬门槛` / `dsr 与 walk_forward 至少保留其一` |
| 预检通过 | 清单只读预览态，显示可行性预判 |
| 已冻结 | 只读 + `spec_id`；顶部提示「验证清单已随协议冻结」 |
| 运行中查看 | 只读，跳到 F10 验证进度 |

#### 3.4.8 边界

- 配置页不改参数网格，不改预算，不改假设。它只回答「用什么标准判定」。
- 不提供阈值输入框。
- 不提供「本轮先不判定，跑完再决定」的模式——那等于取消预先声明。
- 不提供自定义验证点（写自己的检验函数）。首版验证点集合是封闭的；扩展走 DSL 与门槛注册表的版本升级，不走用户输入。
- 配置页不显示任何策略收益预测。

### 3.5 F5 预检与协议冻结

**目标：** 在正式运行前把「会失败的事」提前失败掉，并让用户在一份完整、可读的协议上按下不可反悔的冻结。

**入口：** Before bed 阶段的「预览协议」按钮，或 `Ctrl/Cmd+Enter`；CLI `alphaloop preview --spec PATH`。

**预检检查什么：**

| 类别 | 检查项 | 失败表现 |
| --- | --- | --- |
| 假设可表达性 | 信号机制在允许的 DSL kind 内、是方向性信号 | 明确说明为什么不行（如需要成交量序列） |
| 市场档案 | 档案受支持、基准可用 | 拒绝 |
| 数据快照 | 快照存在、哈希匹配 | `数据快照不可用` / `数据快照哈希不匹配` |
| 验证清单 | 至少一个硬门槛；`dsr` / `walk_forward` 至少其一；类别约束合法 | 拒绝并指向配置页 |
| 可行性预判 | 逐验证点算 `可执行 / 可能跳过 / 必定跳过` | 不拒绝，但必须展示 |
| 预算 | 时间预算为正有限、成本预算非负有限 | 拒绝 |
| 资源 | 磁盘空间、目录可写 | 拒绝 |
| 主机约束 | 输出唤醒约束说明 | 始终展示 |

**协议预览展示什么：**

```text
planned_n_trials: 9

spec_id: rs_<32 位哈希>          （冻结后才最终确定）
statement: <假设陈述>
signal_mechanism: momentum_12_1 — 12-1 momentum
market_profile: us-equity-daily — US equities, NYSE, 5 bps, default SPY
验证清单: 5 项硬门槛 · 1 项放宽 · 逐项见验证方法配置
seed / time_budget_s / cost_budget_usd
方法参数网格: 每行一组 key=value
```

**冻结动作：**

- 按钮文案：`Freeze and submit`（冻结并提交）。
- 冻结按钮默认禁用，仅在「预检成功」且「预检之后未再改动任何输入」时可用。改一个字就重新禁用。这是本产品最重要的一条交互纪律：**冻结的必须是用户刚刚看过的那份协议**。
- 冻结把假设、市场档案、数据快照引用、预算、随机种子、**验证清单**一并写入 `research-spec.yaml`，并由 `spec_id` 内容哈希覆盖（含验证清单，见附录 A）。
- 冻结后立即返回 `run_id`，界面切到任务列表并定位到该任务。

**状态：** 未预检 / 预检中 / 预检失败（错误列表）/ 预检通过（冻结可用）/ 预检通过后被改动（冻结再次禁用）/ 已冻结（返回 `run_id`）。

**边界：** 预检错误**不是**研究结论。预检拒绝的运行不产生 `run_id`，不进任务列表，不产生任何结论。预览不创建任务、不产生 `FOUND`。

### 3.6 F6 任务控制：提交、取消、断点续跑

**目标：** 让用户相信「夜里发生的事我能控制，也能理解」。

**入口：** 任务详情动作区；CLI `alphaloop submit / cancel / resume / status / replay`。

**关键 UI 元素与可见条件：**

| 动作 | 按钮 | 可见条件 | 效果 |
| --- | --- | --- | --- |
| 提交 | `Freeze and submit` | 预检通过且未改动 | 创建任务，返回 `run_id` |
| 取消 | `Cancel` | 状态为 `queued` 或 `running` | 终止 worker，任务转 `cancelled` |
| 续跑 | `Resume` | 状态为 `failed` | 重新入队，从最近一个完整 checkpoint 继续 |
| 重放报告 | `Replay report` | 始终 | 由已封存证据重新生成 `report.md`，不重跑研究 |

**必须披露的三句话**（预检结果与 Help 各出现一次，措辞保持一致）：

1. 主机在本机 worker 运行期间必须保持唤醒。
2. 关闭浏览器或终端**不会**停止任务。
3. 挂起或关机**会**停止计算。

**恢复语义：**

- worker 心跳超期或进程消失 → 守护进程终止残留进程、恢复次数 +1、重新拉起，从最近一个完整 checkpoint 续跑。
- 恢复次数达上限 → 任务转 `failed`，研究结论为 `INCONCLUSIVE`。
- 用户可以对 `failed` 任务点 `Resume`；已封存的 `FOUND` 不会因为后续技术故障被抹掉。

**状态：** 任务状态与研究结论**分两行显示，永不合并**。`Job status: running` 与 `INCONCLUSIVE` 同屏出现时不构成矛盾——前者说进程，后者说证据。

**边界：** 不提供暂停 / 恢复（只有取消与续跑）；不提供优先级与队列重排；不提供修改运行中任务的协议。

### 3.7 F7 进度总览

**目标：** 用户扫一眼就知道「跑到哪了、还剩多少、活着吗」。

**入口：** 任务详情上部，运行中与终态共用。

**关键 UI 元素：**

| 元素 | 内容 |
| --- | --- |
| 搜索进度 | `search: n_trials / planned_n_trials` + 进度条 |
| 预算 | 时间预算与成本预算，以及已消耗与剩余 |
| 检查点 | 最近一个完整 checkpoint 的序号与时间 |
| 心跳 | worker 最近心跳时间 |
| 恢复 | 恢复次数（> 0 时） |
| 错误 | worker 错误信息（有则显示） |

**状态：** 排队中（进度 0，显示「等待 worker」）/ 运行中（进度推进，心跳刷新）/ 恢复中（进度可能回退到 checkpoint 处，需明说「已从检查点 N 续跑」）/ 终态（进度冻结在最终值）。

**边界：** **禁止假进度**。进度条只反映真实完成的试验数与真实检查点推进；不做时间插值动画。剩余时间不做预测性倒计时，只显示预算余量。

### 3.8 F8 试验台账（trial ledger）

**目标：** 任何一条结论都能被追到「具体哪次试验、什么参数、算出了什么」。

**入口：** 任务详情底部，默认折叠。

**关键 UI 元素：** 只读表格，一行一次试验：

| 列 | 内容 |
| --- | --- |
| `trial_id` | 等宽 |
| 信号 kind | `id — 人话` |
| 参数 | `key=value` 空格分隔，空参数显示 `{}` |
| 修订类别 | `none`（首个网格点）/ `method`（后续网格点） |
| 验证结果摘要 | 通过数 / 需要数，失败项高亮（**新增**） |
| 下钻 | 展开该候选的策略验证结果（F13） |

页脚固定说明：台账是 `runs/<run_id>/trial-ledger.jsonl` 的视图；每条记录都计入多重检验计数。

**状态：** 空（尚无试验）/ 增量填充（运行中持续追加，不重排已有行）/ 完整（终态）/ 部分损坏（某行无法解析时跳过该行并显示「N 行无法解析」，不整表报错）。

**边界：** 台账只读、只增。界面不提供删除、编辑、隐藏某次试验的能力——那会破坏多重检验计数的完整性。

### 3.9 F9 候选漏斗

**目标：** 回答「为什么这一轮没有东西入围」，并把答案变成下一次的行动依据。

**入口：** 任务详情，证据摘要下方。

**关键 UI 元素：**

- 汇总行：`已评估 N · 通过 N · 未通过 N · 证据不完整 N`
- 堆叠条：通过 / 未通过 / 证据不完整三段，配色与三结论体系一致
- 主因列表：按失败次数降序的门槛，`<门槛释义> × <次数>`，配比例条
- 每个主因可展开到受影响的候选列表

**状态：** 空（`none`）/ 部分（运行中随试验推进更新）/ 完整（终态）。

**边界：** 漏斗**只读**。界面不提供「放行这个候选」「忽略这一关」的操作——证据门槛不可在界面被覆盖（上游 §9.3）。这条约束由测试锁定：控制台脚本中不允许出现 override 语义的控件。

### 3.10 F10 验证进度（**新增**）

**目标：** 运行中就能看见「验证清单跑到哪一项了」，而不是等终态才知道结果。

**入口：** 任务详情，进度总览下方；运行中默认展开，终态自动收起为 F13 的入口。

**关键 UI 元素：** 与 F4 的配置清单**同构**（同样的分组、同样的缩进、同样的释义），只是把复选框换成状态徽标：

```text
验证进度                          硬性检验 已完成 3 / 5 · 当前候选 c_0004

硬门槛
  dsr                pass        DSR 0.962 · 按 9 组试验去膨胀 · OOS 收益
  walk_forward       incomplete  自身 OOS 平均 Sharpe 0.41，但 cpcv 被跳过
    regime_stability pass
    median_fold      pass
    majority_folds   pass
    cpcv             skipped     分组样本不足
  vs_benchmark       running
全轮硬校验
  net_of_cost        pass        5 bps × 换手已扣除
  nested_holdout     pending
诊断项
  pbo                pending     不影响 FOUND
```

完成度计数器只数**有否决权的**验证点，即顶层硬门槛加全轮硬校验。绑定子校验随父门槛计入，诊断项不计入——否则一个诊断项跑完会让用户误以为结论更近了一步。

**逐验证点状态：**

| 状态 | 含义 | 视觉 |
| --- | --- | --- |
| `pending` | 已在清单中，尚未执行 | 中性灰 |
| `running` | 正在执行 | 焦点色 + 脉冲 |
| `pass` | 通过 | 通过色 |
| `fail` | 未通过 | 告警色 |
| `skipped` | 前置条件不满足，未能执行 | 告警色 + 必须带原因 |
| `incomplete` | 自身有结果，但其启用的绑定子校验被跳过，因此不计为通过 | 未定色 + 必须说明是哪一项 |
| 未启用 | 冻结时未选入清单 | 不出现在进度里（可通过「显示未启用项」查看） |

`incomplete` 是本设计新增的一等状态。它存在的唯一理由是：一个门槛「自己算出来是正的、但少了一项该做的检验」既不是通过也不是失败，界面必须能把这件事说清楚，而不是被迫二选一。

**`skipped` 的结论语义（本设计对现状的收紧）：**

| 被跳过的对象 | 对结论的影响 |
| --- | --- |
| 硬门槛 | 该门槛在证据集中缺席 → 证据不完整 → `INCONCLUSIVE`。**绝不当作通过。** |
| 绑定子校验（硬） | 父门槛转为 `incomplete`，不得仅凭自身通过而计为 `pass` → `INCONCLUSIVE` |
| 全轮硬校验 | 本轮证据不完整 → `INCONCLUSIVE` |
| 诊断项 | 仅记录，不影响结论 |

现状是绑定子校验（如 CPCV、嵌套留出）在样本不足时静默缺席，父门槛照常通过。本设计要求把这种缺席显式化为 `skipped` 并降级结论。这会让一部分原本 `FOUND` 的运行变成 `INCONCLUSIVE`——这正是目的：**沉默的宽松比明确的「证据不足」危险得多。**

**跳过原因取值：** `insufficient_sample`（样本不足）、`missing_secondary_source`（缺第二数据源）、`missing_benchmark_series`（缺基准序列）、`engine_error`（引擎错误）。每个原因在界面上都有对应的人话解释，不直接暴露标识符。

**状态：** 排队中（全部 `pending`）/ 运行中（逐项推进，按候选切换）/ 终态（定格）/ 无数据（运行尚未产出任何门槛结果时显示清单与全 `pending`，不显示空白）。

**边界：** 验证进度是观测面板，没有任何控件能改变清单或结果。运行中不允许增删验证点。

### 3.11 F11 结论页：唯一主结论

**目标：** 五分钟读懂。第一屏只需回答一个问题：**这一轮的结论是什么。**

**入口：** 任务列表选中任一任务；CLI `alphaloop status <run_id>`。

**关键 UI 元素（自上而下，顺序固定）：**

1. **主结论**：`FOUND` / `NO_EVIDENCE` / `INCONCLUSIVE` 单词，最大字号，独立配色。
2. **一句解释**：三句固定文案之一（措辞已锁定，见 §5.2）。
3. **主要证据**：`FOUND` 时为「所有必需硬门槛均通过」；`NO_EVIDENCE` 时为「<某门槛> 未通过」；`INCONCLUSIVE` 时为「缺少 <门槛列表>」或「无已封存的门槛证据」。
4. **停止原因**：`all_gates_passed` / `hard_gate_failed` / `incomplete_evidence`；非终态显示「（运行中或尚未终结）」。
5. **放宽徽标**（**新增**）：`本轮放宽 N 项`，可展开。N = 0 时不显示。
6. **任务状态区**：任务状态、心跳、恢复次数、worker 错误，与结论视觉分离。

**状态：**

| 状态 | 主结论区表现 |
| --- | --- |
| `queued` / `running` | 结论显示 `NONE`，解释说明「任务状态不是研究结论」；主要证据与停止原因显示「（运行中或尚未终结）」 |
| `completed` + 全门槛通过 | `FOUND` |
| `completed` + 证据完整但有失败 | `NO_EVIDENCE` |
| `completed` + 证据不完整 | `INCONCLUSIVE` |
| `failed` / `cancelled` | `INCONCLUSIVE`，除非已有更早封存的 `FOUND` |
| 无任何任务 | 空态引导 + 不承诺 alpha 声明 |

**边界：** 一次运行只有一个主结论，不出现「部分成功」「接近通过」「置信度 87%」等中间态措辞。不显示收益曲线作为视觉主体——结论页的中心是判决，不是业绩展示。

### 3.12 F12 证据摘要

**目标：** 让主结论可被检验，而不是被相信。

**入口：** 结论页主结论下方。

**关键 UI 元素：** 每个必需门槛一行：

```text
<门槛释义>: pass|fail · <关键指标>=<值> · <关键指标>=<值>
```

展示的关键指标按门槛类型选取，例如：收益口径（OOS / 内层 / 全样本）、试验数、DSR 值、OOS Sharpe 均值与中位数、前后半段 Sharpe、regime 是否稳定、fold 数与正 fold 数、多数是否稳定、CPCV 与 PBO 与留出段的对应指标。

每行可展开到该门槛在 `runs/<run_id>/evidence/` 下的原始输入引用（文件与键路径），并附一句「报告是证据的视图，不是证据的来源」。

**状态：** 无已封存证据（说明「无已封存的门槛证据」并解释这会导致 `INCONCLUSIVE`）/ 部分（运行中）/ 完整（终态）。

**边界：** 证据摘要不做跨运行对比，不做排行榜。不同市场档案的候选不进同一个默认排名（上游 §5.5）。

### 3.13 F13 策略验证结果（**新增**，核心）

**目标：** 对每一个候选策略——入围的和被淘汰的——回答「它在我选的每一项验证上表现如何」，并且每一条都能下钻到证据。

这是 F4 的对偶：F4 让用户在开始前**选**验证方法，F13 让用户在结束后**按同一份清单读**结果。两者的分组、顺序、释义完全一致，用户不需要在两处建立两套心智模型。

**入口：** 两处，同一组件：

1. **结论页**：入围候选列表中每一行可展开为验证结果面板。
2. **策略详情**：从入围候选、候选漏斗主因、试验台账任意一处点进的候选详情面板（同一 `run_id` 内的面内下钻，不新开路由）。

**关键 UI 元素：**

入围候选：

```text
c_0004 · momentum_12_1 — 12-1 momentum · lookback=126 skip=21
状态: 入围（所有必需硬门槛通过）              导出 .asb

硬门槛                          结果      关键指标                     证据
  dsr                           pass      dsr=0.962 n_trials=9        evidence/trials/c_0004.json
  walk_forward                  pass      oos_sharpe_mean=0.41        evidence/trials/c_0004.json
    regime_stability            pass      前半 0.38 · 后半 0.44
    median_fold                 pass      中位 0.36
    majority_folds              pass      5/7 fold 为正
    cpcv                        pass      路径均值 0.34 · 中位 0.31
  vs_benchmark                  pass      策略 0.41 · 基准 0.28
全轮硬校验
  net_of_cost                   pass      5 bps × 换手已扣除
  nested_holdout                pass      留出段 Sharpe 0.33 · n=63
诊断项（不决定结论）
  pbo                           pass      pbo=0.31 · 阈值 0.5 · 放宽为诊断

本轮放宽 1 项：pbo 由全轮硬校验降级为诊断。
该结果不构成 alpha 或未来盈利的承诺。
```

淘汰候选与证据不完整候选用同一套结构，只是结果列不同，并把首个需要注意的行置顶高亮：

```text
c_0002 · momentum_12_1 — 12-1 momentum · lookback=189 skip=21
状态: 淘汰（walk_forward 未通过）

硬门槛                          结果        关键指标
  walk_forward                  fail        oos_sharpe_mean=-0.12   ← 首个失败
  dsr                           pass        dsr=0.951 n_trials=9
  ...

c_0007 · momentum_12_1 — 12-1 momentum · lookback=126 skip=42
状态: 证据不完整（cpcv 被跳过）— 这不是「几乎通过」

硬门槛                          结果        关键指标
  walk_forward                  incomplete  自身 0.22，但 cpcv 被跳过   ← 需注意
    cpcv                        skipped     分组样本不足
  ...
```

必备元素：

1. **候选身份行**：`trial_id` · 信号释义 · 参数。
2. **候选状态**：入围 / 淘汰（附首个失败门槛）/ 证据不完整（附缺失项）。
3. **逐验证点表**：分组与缩进与 F4、F10 完全一致；列为 结果 / 关键指标 / 证据链接。
4. **证据下钻**：每行指向 `runs/<run_id>/evidence/trials/<candidate_id>.json` 内的具体键路径。
5. **放宽提示**：若本轮有放宽，在候选面板底部重复一次——用户可能是直接从台账跳进来的，没看过结论页顶部。
6. **导出入口**：仅当研究结论为 `FOUND` 且该候选在已封存证据中时出现。
7. **反夸大声明**：面板底部固定一句。

**淘汰候选也要展示。** 这是刻意的设计：研究的价值经常在于「它死在哪一关」。淘汰候选的面板结构完全相同，只是结果列出现 `fail`，并把首个失败门槛置顶高亮。

**状态：**

| 状态 | 表现 |
| --- | --- |
| 无候选 | `none`，并说明可能原因（无试验完成 / 全部证据不完整） |
| 运行中的候选 | 已完成的验证点显示结果，未完成显示 `pending`，不显示半成品指标 |
| 入围 | 全部必需硬门槛 `pass` |
| 淘汰 | 至少一项必需硬门槛 `fail` |
| 证据不完整 | 至少一项必需硬门槛为 `skipped`、`incomplete` 或缺席；明确说明这不是「几乎通过」 |

**边界：** 面板只读。不提供「重跑这个候选」「把这个候选标记为通过」的操作。不显示未来收益预测、不显示建议仓位、不显示任何交易相关字段。

### 3.14 F14 方法修订复盘

**目标：** 让用户知道「夜里这台机器替我改了什么」，并确认它没有偷偷改掉假设。

**入口：** 结论页，候选漏斗下方。

**关键 UI 元素：** 每行 `<trial_id> · <修订类别> · <信号释义> · <参数>`。修订类别只有两种：

| 类别 | 含义 | 是否允许在本轮执行 |
| --- | --- | --- |
| `method` | 方法性修订：参数覆盖、实现细节修复、成本假设补齐、数据修复 | 允许，且计入多重检验计数 |
| `economic` | 经济性修订：经济逻辑、信号机制、市场范围、基准、**验证清单**中任一项改变 | **不允许**，转入下一假设队列 |

**验证清单的变更属于经济性修订**，与现有实现一致：改判定标准和改假设一样，都会让原来的预先声明失效。界面必须把这一点讲明白，否则用户会以为「只是调了个检验项」。

**状态：** 空（`none`，说明「本轮未发生方法性修订」）/ 有修订（列表）/ 有经济性修订被排队（指向 F15）。

**边界：** 复盘只读。不提供「撤销这次修订」。

### 3.15 F15 下一假设建议队列

**目标：** 把「这次学到了什么」变成下一次的起点，同时严守「新经济假设绝不在同一次隔夜运行里静默执行」。

**入口：** 结论页下部；`FOUND` 与 `NO_EVIDENCE` 都可能产生建议——没有证据同样有信息量。

**关键 UI 元素：**

- 建议列表：每条一句假设陈述 + 排队原因（如 `economic_change_queued`，界面显示人话）。
- 「载入编辑器」按钮：把建议填回 F3 表单并**自动触发一次协议预览**，用户看到的是一份完整的新协议，而不是一段文本。
- 「下一步」提示：结论页顶部附近显示第一条建议，作为明确的下一步动作。

**关键约束：** 载入建议 = 新研究。它会得到新的 `spec_id`、新的 `run_id`、新一轮验证方法配置（默认继承上一轮的清单，包括放宽项，并在配置页显式提示「继承自 <上一 run_id>，含 1 项放宽」）。它**不会**复用上一轮的证据，也不会自动提交。

**状态：** 空（`none`）/ 有建议（列表 + 下一步提示）/ 已载入（表单被填充，冻结按钮因「尚未预检通过」保持禁用直至预览完成）。

**边界：** 建议**只是建议**。产品不排序建议的「胜率」，不预测建议的收益，不自动执行任何一条。

### 3.16 F16 .asb 导出与交接

**目标：** 把一个 `FOUND` 候选变成不可变、可校验、自带血缘的数据包，交给 AlphaStrategy；并在这一步把边界说清楚。

**入口：** 结论页交接区（仅 `FOUND`）、候选验证结果面板、CLI `alphaloop export <candidate_id> --output strategy.asb`。

**关键 UI 元素：**

- 交接区：`入围: <candidate_id> · <信号释义> · <参数>` + `导出 .asb` 按钮。
- 导出回执：结论词、入围候选、导出路径、以及固定的「本次导出不构成 alpha 或未来盈利的承诺」。
- 内容说明（可展开）：包内含 DSL 文档、冻结参数、市场档案、研究阶段风险假设、完整运行与证据血缘、一致性校验固件、内容哈希；**不含**任何可执行文件、不含凭据。
- 放宽清单（**新增**）：导出包的血缘中记录本轮验证清单与放宽项；导出回执中提示「本包的结论是在放宽 N 项的标准下得到的」。

**状态：** 不可导出（非 `FOUND`，按钮不出现；CLI 明确拒绝并说明需要 `FOUND`）/ 可导出 / 导出中 / 成功（回执）/ 失败（候选不在已封存证据中、路径不可写等，逐条说明）。

**边界（硬墙）：** 导出是一次**人工动作**，不自动触发。alphaloop 不连接券商、不下单、不调用 AlphaStrategy 的执行接口、不自动晋级到模拟盘或实盘。导入不等于授权交易——晋级是 AlphaStrategy 侧独立的人工审批流程。集成是单向的：alphaloop → `.asb` → AlphaStrategy，没有回传遥测。

### 3.17 F17 次要入口：CLI 与 Agent Skill

**目标：** 服务已经在用编码 agent 的用户，但不把主路径搬到命令行。

**CLI（首版覆盖完整生命周期）：**

| 命令 | 作用 |
| --- | --- |
| `alphaloop start` | 启动本机控制面与打包好的 Web 控制台 |
| `alphaloop dataset <path>` | 缓存数据快照，返回内容寻址 id 与哈希 |
| `alphaloop preview --spec PATH` | 预检 + 协议预览（含验证清单与可行性预判），不创建任务 |
| `alphaloop submit --spec PATH` | 冻结并提交，立刻返回 `run_id` |
| `alphaloop status [run_id]` | 结论、主要证据、停止原因、漏斗、验证清单结果 |
| `alphaloop cancel [run_id]` | 取消 |
| `alphaloop resume [run_id]` | 从 checkpoint 续跑 |
| `alphaloop replay [run_id]` | 由已封存证据重生成报告 |
| `alphaloop export <candidate_id>` | 导出 `.asb` |

CLI 输出遵循与界面相同的结论优先顺序：结论词 → 一句解释 → 主要证据 → 停止原因 → 漏斗 → 修订 → 下一步 → 入围候选 → 任务状态 → 不承诺 alpha 声明。长任务返回 `run_id`，不占着一个同步会话不放。

**Agent Skill：** 教编码 agent 做四件事——构造并预检假设、提交后**轮询而不是阻塞**、正确解释三种结论、在需要新假设或导出时请求人工确认。Skill 是工作流指引，不是服务，也不是证据引擎。

**边界：** 首版不含 MCP 适配器。未来的 MCP 只做短异步操作（创建 / 查状态 / 取结果 / 取消），任何 MCP 调用都不允许挂着一整夜。

## 4. 流程

### 4.1 主流程

```text
[F1] 启动本机                 alphaloop start → 守护进程可接单
        │
[F3] 定义研究                 假设 + 市场档案 + 数据快照 + 预算
        │
[F4] 配置验证方法             默认清单（市场档案 ⊕ 协议模板）→ 用户调整 → 放宽留痕
        │
[F5] 预检                     可表达性 / 数据 / 清单合法性 / 可行性预判 / 预算 / 资源 / 主机约束
        │                     ├─ 失败 → 回到 F3 或 F4（不产生 run_id）
        │                     └─ 通过 → 协议预览（含验证清单终确认）
        │
[F5] 冻结                     research-spec.yaml + spec_id（覆盖验证清单）→ 返回 run_id
        │
[F6] 运行                     worker 独立于浏览器与终端；checkpoint 持续写入
        │
[F7/F8/F9/F10] 观测           进度 / 台账 / 漏斗 / 逐验证点状态
        │
        │                     停止：全门槛通过 · 门槛失败且网格耗尽 · 预算耗尽 · 经济性修订被排队
        │
[F11] 结论                    FOUND / NO_EVIDENCE / INCONCLUSIVE（唯一主结论）
        │
[F12/F13/F14] 复盘            证据摘要 / 每候选逐验证点结果 / 方法修订
        │
        ├─[F16] FOUND → 人工导出 .asb → AlphaStrategy（单向，导入不等于授权交易）
        └─[F15] 任意结论 → 下一假设建议 → 载入编辑器 → 新 spec_id 的下一轮
```

### 4.2 异常流程

| # | 异常 | 触发 | 产品行为 | 结论影响 |
| --- | --- | --- | --- | --- |
| E1 | 假设无法用 DSL 表达 | 预检 | 拒绝并说明为什么（如需要成交量序列 / 是波动率特征而非方向性信号） | 无 `run_id`，无结论 |
| E2 | 数据快照缺失或哈希不符 | 预检 / 重放 | 拒绝，明确区分「不可用」与「哈希不匹配」；重放**失败关闭**，不用近似数据凑 | 无结论 / 重放失败 |
| E3 | 验证清单不合法 | 预检 | 拒绝并跳回配置页高亮违规项（如「至少保留一个硬门槛」） | 无 `run_id` |
| E4 | 清单含「必定跳过」的硬门槛 | 预检 | **不拒绝**，但冻结确认页显著提示「按当前清单，本轮最好的结果是 `INCONCLUSIVE`」 | 用户坚持则最终 `INCONCLUSIVE` |
| E5 | 预算不足 / 磁盘不足 / 目录不可写 | 预检 | 拒绝并给出具体数字 | 无 `run_id` |
| E6 | 单个候选计算失败 | 运行中 | 隔离，淘汰该候选，其余继续；台账记录 | 不影响整轮 |
| E7 | 验证点前置条件不满足 | 运行中 | 标记 `skipped` + 原因；硬门槛、其绑定子校验或全轮硬校验被跳过则证据不完整 | `INCONCLUSIVE` |
| E8 | 数据完整性或诊断引擎故障 | 运行中 | 停止整轮，记录错误 | `INCONCLUSIVE` |
| E9 | worker 崩溃（可恢复） | 运行中 | 心跳超期 → 终止残留 → 恢复次数 +1 → 从最近完整 checkpoint 续跑 | 不影响结论 |
| E10 | worker 不可恢复（恢复次数耗尽） | 运行中 | 任务转 `failed`，显示 worker 错误与恢复次数，提供 `Resume` | `INCONCLUSIVE` |
| E11 | 主机挂起 / 关机 | 运行中 | 计算停止（已在预检披露）；唤醒后由 `Resume` 从 checkpoint 续跑 | 续跑成功则不影响 |
| E12 | 时间或成本预算耗尽 | 运行中 | 正常停止，停止原因为预算耗尽 | 证据不完整时 `INCONCLUSIVE` |
| E13 | 门槛失败且冻结网格已耗尽 | 运行中 | 停止搜索，**不扩大已失败的搜索空间** | `NO_EVIDENCE` |
| E14 | PBO 在 FOUND 时刻未通过 | 结论生成 | 从 `FOUND` 降级；证据行明确写出 PBO 值与阈值。若用户已把 `pbo` 降级为诊断，则不降级结论，但结论页与 `.asb` 血缘记录该放宽 | `FOUND` → `NO_EVIDENCE`（`pbo` 为诊断时保持 `FOUND`） |
| E15 | 提出经济性修订（含改验证清单） | 运行中 | 停止本轮搜索，转入下一假设队列，等人工审核 | 按已有证据定结论 |
| E16 | 用户取消 | 运行中 | 终止 worker，任务转 `cancelled` | `INCONCLUSIVE`（除非已有更早封存的 `FOUND`） |
| E17 | 对非 `FOUND` 请求导出 | 导出 | 拒绝并说明需要 `FOUND` | 无 |
| E18 | 导出候选不在已封存证据中 | 导出 | 拒绝并说明该候选未在封存证据里 | 无 |
| E19 | 台账某行无法解析 | 展示 | 跳过该行，显示「N 行无法解析」，其余照常渲染 | 无 |
| E20 | 守护进程未运行 | 任意 | 页面不可达；CLI 提示先 `alphaloop start` | 无 |

**贯穿所有异常的两条纪律：**

1. **失败关闭。** 缺失、损坏、部分的证据一律不能产出 `FOUND` 级别的乐观结论；只能是 `INCONCLUSIVE`。
2. **技术故障不是研究结论。** worker 崩溃说明这台机器出了问题，不说明假设不成立。界面必须让这两件事在不同的行里。

### 4.3 状态机

**任务状态**（进程视角）：

```text
queued ──> running ──> completed
             │  ├────> failed ──(Resume)──> queued
             │  └────> cancelled
             └──(心跳超期/进程消失, 恢复次数+1)──> running
```

**研究结论**（证据视角）：

| 任务状态 | 证据完整 | 全门槛通过 | 结论 |
| --- | --- | --- | --- |
| `queued` / `running` | — | — | `NONE` |
| `completed` | 是 | 是 | `FOUND` |
| `completed` | 是 | 否 | `NO_EVIDENCE` |
| `completed` | 否 | — | `INCONCLUSIVE` |
| `failed` / `cancelled` | — | — | `INCONCLUSIVE`（除非已有更早封存的 `FOUND`） |

`failed` 或 `cancelled` 的任务**不能**声称 `FOUND`。

## 5. 交互原则与文案规则

### 5.1 五条交互原则

**原则一：结论优先。** 任何展示研究结果的界面（结论页、CLI 输出、报告、导出回执）都以结论词开头，其余按 §2.4 的固定顺序往下沉。不允许因为某段内容更丰富就把它提到结论之前。

**原则二：识别优于回忆。** 用户应当看到可选的信号机制、市场档案、验证点，而不是记住 YAML 键名和门槛标识符。每个标识符旁边都有 `id — 人话` 释义。

**原则三：判决标准先于结果。** 判定成功的标准必须在研究开始前被看见并冻结。冻结之后不能改标准，也不能在界面上覆盖已产出的门槛结果。界面里不存在 override 控件。

**原则四：诚实的进度。** 不做假进度、不做预测性倒计时、不做粒子与霓虹脉冲。动效只用于真实的检查点推进与面板展开（120–180ms 淡入、4px 位移），并尊重系统的减少动态效果设置。所有运行状态在静止时都应可读。

**原则五：一处放宽，处处可见。** 相对默认标准的任何削弱都在配置页、冻结确认页、结论页、`.asb` 血缘四处出现。产品允许用户放宽，不允许放宽被隐藏。

### 5.2 三结论语义与固定文案

三个结论词在任何界面上都以英文原词呈现（`FOUND` / `NO_EVIDENCE` / `INCONCLUSIVE`），配色互不相同，且各带一句已锁定的解释文案：

| 结论 | 含义 | 固定解释（现有实现，措辞不得改动） |
| --- | --- | --- |
| `FOUND` | 每个必需硬门槛都到齐且通过 | `FOUND means every required hard gate is present and passed. It is not a promise of alpha.` |
| `NO_EVIDENCE` | 某个必需硬门槛未通过 | `NO_EVIDENCE means a required hard gate failed. It is not a promise that alpha does not exist.` |
| `INCONCLUSIVE` | 证据集不完整 | `INCONCLUSIVE means the evidence set is incomplete. Missing diagnostics cannot produce FOUND.` |
| 非终态 | 任务状态不是研究结论 | `Job status (queued, running, completed, failed, cancelled) is not the research conclusion.` |

三条推论，界面必须体现：

1. `NO_EVIDENCE` **不是**失败态。它是一个信息量充足的结论，配色独立、有下一步建议、可以产生下一假设。不用红色，不用「失败」「错误」措辞。
2. `INCONCLUSIVE` **不是**「差一点通过」。它表示「不知道」。界面禁止出现「接近通过」「仅缺一项即可通过」这类暗示。
3. 缺失的诊断**不能**产出 `FOUND`。这一条是产品最重要的安全承诺，也是 `skipped` 必须降级结论的原因。

### 5.3 文案规则

**必须做：**

- 门槛、信号、市场档案、跳过原因一律 `标识符 — 人话` 双写。标识符保持英文小写下划线形式（`dsr`、`walk_forward`、`vs_benchmark`），便于与 CLI、YAML、证据文件对照。
- 门槛判定结果用小写 `pass` / `fail`，与证据文件一致。
- 每个展示结论或导出结果的界面都带一句反夸大声明。
- 任务状态与研究结论分行，永不合并成一个身份串。
- 数字带口径。写「OOS 平均 Sharpe 0.41」而不是「Sharpe 0.41」；写「按 9 组试验去膨胀后 DSR 0.962」而不是「DSR 0.962」。

**禁止做（禁用词表，适用于界面、CLI 输出、报告与导出回执）：**

| 类别 | 禁止出现 |
| --- | --- |
| 交易暗示 | 买入、卖出、开仓、仓位建议、止损、下单、实盘、模拟盘、上线、部署、晋级 |
| 收益承诺 | 预期收益、年化回报预测、胜率、盈利概率、发现 alpha、稳定赚钱 |
| 夸大与暗示 | 接近通过、几乎通过、大概率有效、值得一试、推荐使用 |
| 拟人化权威 | AI 认为可以、模型建议买入、智能推荐 |
| 界面能力 | override、强制通过、忽略此门槛、标记为通过 |
| 社交与竞技 | 排行榜、收益榜、跟单、分享战绩 |

**语言选择：** 界面文案首版为英文（已被 e2e 锁定，本文档不要求改）。本设计文档用中文书写，产品术语保留英文原词：`FOUND`、`NO_EVIDENCE`、`INCONCLUSIVE`、`run_id`、`spec_id`、`.asb`、`checkpoint`、`trial ledger`、`hard gate`、`OOS`、`DSR`、`PBO`、`CPCV`。这些词是用户与 CLI、YAML、证据文件之间的共同词汇，翻译反而增加对照成本。

### 5.4 视觉与配色语义

配色承载语义，不承载装饰。以下映射已被 e2e 锁定，本设计沿用：

| 语义 | 用途 |
| --- | --- |
| 通过色（绿） | `FOUND`、门槛 `pass`、冻结动作 |
| 告警色（琥珀） | `NO_EVIDENCE`、门槛 `fail`、`skipped`、续跑动作 |
| 未定色（紫） | `INCONCLUSIVE`、证据不完整、验证点 `incomplete` |
| 焦点色（蓝） | 操作、焦点、运行中、预览与取消动作 |
| 红色 | **仅**用于技术故障与危险操作，绝不用于 `NO_EVIDENCE` |

`FOUND` 的专用绿色**必须**与「证据集完整」同时出现，不允许在证据不完整时以任何形式出现。

排版：中性无衬线承载叙述；等宽字体仅用于标识符、状态、参数、哈希。

## 6. 首版范围与非目标

### 6.1 首版包含

**入口与运行**

- 一条命令启动本机控制面与打包好的 Web 控制台（用户不需要装 Node）。
- 本机健康与主机唤醒约束披露。
- 研究任务列表（历史 / 进行中 / 已完成），键盘可导航。
- 提交、取消、从 checkpoint 续跑、重放报告。
- worker 独立于浏览器与终端；心跳与自动恢复。

**研究定义**

- 引导式假设表单 + 等价 YAML 入口，双向同步。
- 两个市场档案：`us-equity-daily`、`crypto-daily`。
- 内容寻址的数据快照（上传或引用），重放失败关闭。
- 受约束 DSL 的方向性信号机制，参数网格由信号机制决定。
- **验证方法配置**：验证点登记表、硬门槛 / 绑定子校验 / 全轮硬校验 / 诊断项四类、市场档案 ⊕ 协议模板默认、可行性预判、放宽留痕、随协议冻结。
- 预检与协议冻结，含验证清单终确认；`spec_id` 覆盖验证清单。

**观测与结论**

- 进度总览（预算、试验、检查点、心跳），无假进度。
- 试验台账（只读、只增、全部计入多重检验计数）。
- 候选漏斗与淘汰主因，只读，无 override。
- **验证进度**：逐验证点 `pending` / `running` / `pass` / `fail` / `skipped`（含原因）/ `incomplete`。
- 唯一主结论 + 主要证据 + 停止原因。
- 证据摘要，可下钻到 `evidence/`。
- **策略验证结果**：每个入围与淘汰候选逐验证点结果，结论页与策略详情共用同一组件。
- 方法修订复盘；经济性修订（含改验证清单）转人工队列。
- 下一假设建议队列，只建议不执行。

**交接**

- 人工触发的不可变 `.asb` 导出，仅 `FOUND` 可导；血缘含验证清单与放宽项。
- 包内无可执行文件、无凭据；导入不等于授权交易。

**次要入口**

- 完整生命周期的 CLI，长任务返回 `run_id`。
- 本机 Agent Skill：预检、轮询而非阻塞、正确解释三结论、新假设与导出请求人工确认。

### 6.2 首版非目标

**能力上明确不做（产品边界，不是排期问题）**

- 不交易：不持有券商凭据、不连券商、不下模拟盘或实盘单、不调用 AlphaStrategy 执行接口。
- 不自动晋级：任何候选都不会自动进入模拟盘或实盘；导出是人工动作，导入之后的晋级归 AlphaStrategy。
- 不做团队协作：首版一人一机，没有身份、权限、审批流、共享工作区。
- 不覆盖证据门槛：界面、报告、LLM 都不能改门槛结果；不存在 override 控件。
- 不执行任意生成代码：候选是 DSL 文档（`kind` + 冻结参数），不是新的 Python 类；`.asb` 内不含 `.py`、字节码、wheel、脚本、notebook 或任何二进制载荷。
- 不在同一轮里静默执行新经济假设。

**首版不做（未来可能做）**

- 长连接的 MCP 隔夜调用。首版无 MCP 适配器；未来的 MCP 只做短异步操作。
- 云端 worker。本机执行是默认；未来的用户自有云 worker 必须实现同一套 Job API、状态机、worker 协议与产物契约。
- 桌面壳。本机守护进程 + 打包 Web 控制台已经够用，先不承担跨平台桌面维护成本。
- Bundle Registry。`.asb` 的 schema 保留可选的注册表地址字段，首版不要求也不运营注册表。
- 自定义验证点（用户自带检验函数）与可调阈值。前者走门槛注册表的版本升级，后者会打开「调到通过为止」的后门。
- 跨运行 / 跨市场档案的候选排名。跨市场只做可移植性检验，不比较绝对 Sharpe。
- 界面文案的中文本地化。术语与 CLI、YAML、证据文件共享词汇，本地化需要连同这几处一起规划。
- 冻结的 Vite SPA（`webui/`）改造。它服务的是历史 loop 运行的产物浏览，本设计的所有界面落在打包控制台。

## 附录 A：数据契约增量

本节说明为支撑 F4、F10、F13 需要在契约上增加什么。这是设计意图，不是实现方案；实现细节留给运行时规格。

### A.1 冻结的验证清单

验证清单必须与假设同等级地被冻结，并被 `spec_id` 的内容哈希覆盖。这意味着：

- 清单是 `research-spec.yaml` 的一部分，而不是旁挂的配置文件。
- 增加清单字段会改变 `spec_id` 的计算输入，属于 schema 版本升级；旧 spec 的 `spec_id` 必须仍能校验通过。
- 现有的 `success_criteria.hard_gates` 保持存在，作为「顶层硬门槛 id 列表」这一子集的向后兼容视图；新的清单字段承载 `class`、`scope`、`attaches_to`、`enabled`、来源与放宽标记。
- 冻结时一并记录：清单的默认来源（市场档案 + 协议模板的版本）、用户改动、放宽项与原因。这样才能回答「当时的默认是什么、用户改了什么」。

### A.2 运行期的逐验证点状态

运行期需要一份可增量更新、可被界面轮询的验证进度：逐验证点的 `pending` / `running` / `pass` / `fail` / `skipped` / `incomplete`、跳过原因、以及当前正在评估的候选。它是**派生的运行期状态**，不是结论来源；结论仍然只从已封存的门槛证据推导。

`skipped` 必须是一等状态并带原因，不能用「缺席」来表达。这是 §3.10 结论语义收紧的前提：能被表达，才能被降级。

### A.3 每候选的验证结果

每个候选的门槛证据已经是逐候选记录的。为支撑 F13 需要补上：

- 每条结果的 `class`（硬门槛 / 诊断项）、`scope`（顶层 / 绑定 / 全轮）与 `attaches_to`，这样界面才能还原 F4 的分组与缩进。
- `skipped` 状态与原因，以及父门槛的 `incomplete` 状态与导致它的子校验 id。
- 指向原始证据键路径的引用，供下钻。

### A.4 视图载荷

任务详情的视图载荷需要新增三块：冻结的验证清单（含放宽项）、运行期验证进度、每候选验证结果。三者共用同一套验证点标识符与释义，保证 F4、F10、F13 三处界面在措辞与顺序上完全一致。

### A.5 导出血缘

`.asb` 的血缘需要记录本轮验证清单与放宽项。下游拿到一个候选包时，应当能回答「这个 `FOUND` 是在什么标准下得到的」，而不只是「它通过了」。
