# alphaloop 产品设计文档 v0.0.1

**日期：** 2026-08-24
**类型：** 产品设计（Product Design）
**唯一上游依据：** `docs/requirements/product-positioning-requirements.md`

## 0. 这份文档是什么，不是什么

### 0.1 设计文档，不是定位文档

| | 定位文档（上游） | 本设计文档 |
| --- | --- | --- |
| 回答 | 为什么存在、给谁、边界在哪 | 有哪些功能、长什么样、怎么走完一遍 |
| 产出 | 品类、目标用户、成功标准、架构边界、安全语义 | 功能地图、逐功能规格、状态机、主流程与异常流程、文案规则 |
| 变更方式 | 定位变了才改 | 功能取舍变了就改 |

本文档**继承而不重述**上游的以下结论，并把它们当作不可协商的约束：

- 三结论语义 `FOUND` / `NO_EVIDENCE` / `INCONCLUSIVE`（上游 §1、§6.3）。
- 证据权威：只有确定性硬门槛评估器能产出 `FOUND`；Web 控制台、LLM 评审、报告生成器、agent 叙述都不能覆盖门槛；缺失、损坏或不完整的证据阻止 `FOUND`（上游 §9.3）。
- 交易硬墙：不持有券商凭据、不连接券商、不提交模拟或实盘订单、不调用 AlphaStrategy 执行接口、不自动晋级候选（上游 §9.4）。
- 本机优先：Web 控制台是主要的长任务界面，durable Job API 是架构边界，本机 worker 是默认执行环境，CLI 与 Agent Skill 是本机入口（上游 §1、§10）。
- 一次运行内绝不静默执行新的经济假设；它进入人工审核队列（上游 §4.3、§6.1）。
- 产品不承诺 alpha 或未来盈利；价值在于让 agent 协助的策略研究可复现、可审计、抗自动化 p-hacking（上游 §1）。

### 0.2 场景泛化：从「隔夜」到「随时提交、长时间自主研究、获得可靠结论」

上游用「睡前提交 → 隔夜运行 → 第二天早上读结论」作为叙述场景，并以此表述产品承诺（上游 §1、§4）。

本设计文档把这个场景当作**一个实例**，而不是产品的定义。产品能力的一般形式是：

1. **随时提交** —— 用户在任何时刻定义并冻结一个研究任务，提交后立即拿到 `run_id`（上游 §4.1）。产品不假设提交发生在一天中的某个时刻。
2. **长时间自主研究** —— 任务可以跑数小时。本机 supervisor 让它独立于浏览器与提交用的 shell 存活，checkpoint 让它可恢复，budget 让它可终止（上游 §4.2、§5.1、§5.3）。
3. **获得可靠结论** —— 用户回到界面时，读到唯一主结论、主要证据与停止原因，几分钟内理解发生了什么（上游 §3.4、§4.3）。

「睡前 / 隔夜 / 第二天早上」只是「提交 → 长时间运行 → 回来读结论」在一次睡眠周期上的投影。把它写进产品叙事会带来两个真实的设计损害：

- **它把界面绑在一天中的某个时刻上。** 下午两点提交、晚上七点回来看结论的用户，会在一个叫「早晨」的地方找他的结论。
- **它把「时长」误表述为「时段」。** 需要被设计的属性是「任务可以跑很久且中途无人看管」，与它是否横跨夜晚无关。

因此本文档在**功能命名、界面分区、流程叙述、文案规则**上一律使用随时 / 长时间 / 结论的措辞。§0.4 记录与既有界面标签的关系。

上游依然是唯一的产品依据；本节泛化的是**叙述框架**，不是任何一条约束、语义或范围。

### 0.3 取材边界

本文档的产品内容只来自两处：

1. 上游定位文档。
2. 已明确批准的产品决策（§0.5 列出）。

以下内容**由下游规格拥有，本文档不做断言**：具体门槛与诊断项的清单与阈值常量、界面元素的具体标识符与快捷键绑定、CLI 子命令与参数的完整表、产物文件的精确路径与字段名。本文档只定义这些东西必须满足的**结构与语义**，并在需要举例时使用上游已经点名的概念。

这不是回避细节，而是分层：判定标准的语义归产品设计，判定标准的数值归研究协议与引擎规格。把阈值写进产品文档会制造两份互相漂移的真相。

### 0.4 与既有界面标签的关系

现有控制台可能仍带有以睡眠周期命名的英文分区标签（如 `Before bed` / `Morning`），且这类标签可能已被既有端到端测试锁定。本文档**不要求立即改名**，也不把它们当作功能名。

但**设计目标语言是随时 / 长时间 / 可靠结论的框架**。功能一律以能力命名（如「验证方法配置」「候选漏斗」「结论页」）。遗留标签若保留，视为待收敛的历史外壳，不得反向扩张为产品故事。

### 0.5 已批准的新增产品决策

上游未定义、需在本轮评审确认的决策集中在一条主线上，正文中以「**新增**」标注：

1. **验证方法配置**（§3.4）：提交研究时用户可查看、选择、调整本轮跑哪些验证点，区分硬门槛与诊断项，随研究协议一起冻结。
2. **验证进度**（§3.10）：运行中逐验证点可见 `pending` / `running` / `pass` / `fail` / `skipped` / `incomplete`，并明确 `skipped` 的结论语义。
3. **策略验证结果**（§3.13）：每个入围与淘汰候选按同一份清单逐条展示结果，并可下钻到证据。

三者是同一件事的三个时相——冻结前选、运行中看、结束后读——共用同一套验证点标识、分组与释义。

## 1. 一句话与产品亮点

### 1.1 一句话

> alphaloop 是跑在你自己机器上的自主量化研究实验室：任何时候冻结一个可检验的经济假设，让它在本机长时间无人看管地按预先声明的验证清单跑完，回来时给你一个可审计、可复现、敢于说「没有证据」的结论。

对应的产品承诺（上游 §1 承诺的泛化形式）：

> 一分钟提交，长时间可靠运行，几分钟读懂一个可信的结论。

### 1.2 三个产品亮点

亮点不是「功能多」，而是三件别的工具不做的事。

**亮点一：结论可信（trustworthy conclusion）**

- 一次运行只给**一个**主结论：`FOUND` / `NO_EVIDENCE` / `INCONCLUSIVE`（上游 §1）。
- `FOUND` 的唯一来源是确定性门槛评估器。界面、报告、LLM 评审、agent 叙述都无权覆盖；证据缺一项就退化为 `INCONCLUSIVE`，绝不四舍五入成通过（上游 §9.3）。
- 产品愿意输出坏消息。`NO_EVIDENCE` 是一等结论，有独立视觉标识与独立文案，不是「失败」。
- 所有结论文案都自带反夸大声明：产品不承诺 alpha，也不宣称已证明 alpha 不存在（上游 §1）。

**亮点二：研究可审计（auditable research）**

- 冻结的是完整判决标准：经济逻辑、信号机制、市场范围、基准、成功标准（上游 §6.1），加上本轮的验证清单（§3.4，**新增**）。跑完之后无法追认「我本来就想跑这几项」。
- trial ledger 记录每个候选、每次实验与每次方法性修订，并全部计入多重检验计数（上游 §4.2、§6.1）。
- **放宽留痕**（**新增**）：任何相对默认验证清单的放宽，都会在配置处、冻结确认处、结论页与 `.asb` 血缘里留下标记。放宽是允许的，隐藏放宽是不允许的。
- 每一行证据都能下钻到运行产物里的原始输入。报告是证据的视图，不是证据的来源（上游 §7）。
- 结论可从冻结的协议、数据快照、引擎版本、随机种子与 trial ledger 复现（上游 §3.4）。

**亮点三：长时间运行可恢复（durable long runs on your own machine）**

- 提交后立即返回 `run_id`；任务由本机 supervisor 托管，独立于浏览器与提交用的 shell 存活（上游 §4.1、§4.2、§5.3）。
- 关掉浏览器或终端**不会**停止任务；挂起或关机**会**停止计算。两句都在预检时明说，而不是让用户回来才发现（上游 §4.1）。
- checkpoint 让 worker 崩溃后从最近一个完整检查点续跑；恢复尝试对用户可见（上游 §4.2、§5.1、§9.2）。
- 不可恢复的技术故障转为失败任务与不确定结论，不会伪装成研究结果（上游 §5.3）。
- 数据、代码、结论全部留在本机；控制面默认只绑本机，不在未显式配置时把研究数据暴露到网络（上游 §3.2、§5.1）。

### 1.3 三个恰到好处的惊喜时刻

克制使用，只在能增加信任的地方出现。

1. **冻结时的判决标准收束**：点冻结前，用户看到一份「本轮将检验什么、总共计划试多少组参数、哪些项可能因样本不足被跳过」的清单。它在冻结的瞬间从「可编辑」变成「只读 + 协议指纹」——研究从此有了不可反悔的判决标准。
2. **回来时的唯一判决**：进入结论页，第一屏只有一个词和一句人话解释，其余全部往下沉。用户不需要在十二个图表里自己拼结论。
3. **诚实的跳过**：如果某个验证点因为样本不够没跑成，产品说「跳过 · 样本不足」并把结论降为 `INCONCLUSIVE`，而不是悄悄少算一项然后给 `FOUND`。

### 2.3 界面分区

Web 控制台是单页应用（上游 §5.2）。分区按**能力**而非时刻划分，三个分区正对三段产品能力：

| 分区 | 承载能力 | 对应产品能力 |
| --- | --- | --- |
| **提交区** | F3、F4、F5，以及 F6 的提交动作 | 随时提交 |
| **运行区** | F7、F8、F9、F10 | 长时间自主研究 |
| **结论区** | F11、F12、F13、F14、F15、F16 | 获得可靠结论 |

- F1 常驻顶部，任何分区都能看到本机与运行健康。
- F2 常驻列表栏，进行中与已完成任务同列，不分开两处。
- F6 的取消与续跑落在任务详情，与观测同屏。
- F17 不在页面内。

分区名描述用户此刻在做什么（定义、观测、复盘），不描述现在几点。遗留的以睡眠周期命名的分区标签按 §0.4 处理。

**为什么运行中和终态共用一个界面：** 用户可能中途看一眼，结束后再看一次。同一个 `run_id` 只有一个「任务详情」，随状态演进逐步填满，而不是「运行页」和「报告页」两套心智模型。运行区与结论区是同一份详情的上下两段，不是两个页面。

### 2.4 结论优先的信息层级

任务详情从上到下固定顺序，不允许因为某段内容长就上移（上游 §4.3 的信息顺序，加入 §0.5 的新增能力）：

```text
1  主结论（一个词）+ 一句解释
2  主要证据 + 停止原因
3  任务状态 / 心跳 / 恢复尝试（与研究结论明确分开）
4  验证进度（运行中）或 验证清单结果（终态）
5  入围候选 + 每候选的策略验证结果
6  候选漏斗（淘汰主因）
7  方法修订
8  下一假设建议队列
9  试验台账
10 已封存报告原文
```

上游 §3.4 要求用户能在五分钟内从结论界面识别结论、主要证据与停止原因。前两层就是这条成功标准的直接实现。

## 3. 功能规格

每个功能按 **目标 / 入口 / 关键 UI 元素 / 状态 / 边界** 描述。

### 3.1 F1 本机启动与健康

**目标：** 让用户在三秒内确认「这台机器现在能不能接研究任务，正在跑的任务还活着吗」。

**入口：** `alphaloop start` 启动本机控制面，它同时托管 Job API 与打包好的 Web 应用（上游 §5.1、§5.2）；控制台任何分区顶部常驻健康指示。

**关键 UI 元素：**

| 元素 | 内容 | 说明 |
| --- | --- | --- |
| 本机标记 | 静态 | 声明这是本机运行，数据不出机（上游 §3.2、§5.1） |
| worker 标记 | 空闲 / 运行中及数量 | 当前有几个 worker 在跑 |
| 主机唤醒提示 | 常驻 | 提醒本机 worker 运行期间主机需保持唤醒 |
| 心跳指示 | 最近心跳时间 | 仅当选中任务有心跳时出现（上游 §5.1） |
| 唤醒约束说明 | 固定三句（§3.6） | 在预检结果与帮助处各出现一次 |

**状态：**

| 状态 | 判定 | 界面表现 |
| --- | --- | --- |
| 未启动 | 页面无法加载 | 浏览器错误页；CLI 提示先启动控制面 |
| 空闲可接单 | 控制面健康、无运行中任务 | worker 标记为空闲 |
| 有任务在跑 | 存在运行中任务 | worker 标记显示数量 |
| 正在恢复 | 心跳超期或 worker 进程消失 | 任务卡显示恢复尝试次数，任务保持运行中（上游 §5.1、§9.2） |
| 恢复放弃 | 恢复尝试用尽 | 任务转失败，详情显示 worker 错误（上游 §5.3） |

**边界：** 健康只描述本机控制面与 worker，不代表数据源可用性——那属于预检。控制面默认只绑本机，界面不提供「暴露到网络」的开关（上游 §5.1）。

### 3.2 F2 研究任务列表

**目标：** 一屏扫完「有没有需要我处理的结论」，并能用键盘在任务间移动。

**入口：** 常驻列表栏；冻结提交后自动定位到新任务。

**关键 UI 元素：** 每张任务卡包含

- `run_id`（等宽字体）
- 任务状态：`queued` / `running` / `completed` / `failed` / `cancelled`（上游 §6.3）
- 研究结论：`FOUND` / `NO_EVIDENCE` / `INCONCLUSIVE`，或非终态的空结论
- 冻结时的假设陈述（一行，超出截断）
- 已试验数与计划试验数，及进度条
- 迷你漏斗条（通过 / 未通过 / 证据不完整三段）
- 验证清单摘要（**新增**）：启用的验证点数与放宽项数，放宽数 > 0 时高亮
- 恢复尝试次数（仅 > 0 时出现）

**状态：**

| 状态 | 界面表现 |
| --- | --- |
| 空列表 | 空态引导：如何定义 → 预检 → 冻结提交，并附「不承诺 alpha」声明 |
| 加载中 | 保留上一次列表，不闪空 |
| 有任务 | 按创建时间倒序；运行中任务有活动指示；失败任务有告警边框 |
| 选中 | 卡片高亮，右侧渲染任务详情 |

列表不按「今天 / 昨天」这类时段分组。分组维度是状态（进行中 / 已完成），因为用户关心的是「有没有结论要读」。

**边界：** 列表不做搜索、标签、归档、批量操作。首版一人一机（上游 §3.2、§11），任务量级不需要这些。不同市场档案的候选不进同一个默认排名（上游 §5.5）。

### 3.3 F3 新建研究：假设与市场档案

**目标：** 一分钟内把一个可检验的经济假设变成结构化输入，靠**识别**而不是**回忆**——用户看到可选项，而不是背配置键名。

**入口：** 提交区的引导表单；等价的结构化文本入口作为高级路径，两者双向同步。

**必须冻结的输入**（上游 §6.1 的冻结集合，加上运行参数）：

| 分组 | 输入 | 控件形态 | 说明 |
| --- | --- | --- | --- |
| 假设 | 假设陈述 | 文本 | 一句可判真伪的话 |
| 假设 | 经济逻辑 | 文本 | 为什么应该成立 |
| 假设 | 信号机制 | 从受约束 DSL 允许的机制中选择 | 每项带「标识 — 人话」释义 |
| 市场 | 市场范围 | 文本 | 标的集合 |
| 市场 | 市场档案 | 从受支持档案中选择 | `us-equity-daily` / `crypto-daily`（上游 §5.5） |
| 市场 | 基准 | 文本 | 默认随市场档案填充 |
| 运行 | 随机种子 | 数字 | 复现所需（上游 §3.4） |
| 运行 | 时间预算 | 数字 | 长时间运行的上界（上游 §4.1、§6.2） |
| 运行 | 成本预算 | 数字 | 同上 |
| 数据 | 数据快照 | 引用或上传 | 内容寻址的快照 ID 与哈希（上游 §7） |

上游 §3.3 给的假设形态示例是：「在低波动区间，12-1 动量能否在美国大盘股上产生扣除成本后的样本外超额收益？」——这是产品期望的输入粒度：一个有经济含义的问句，不是「帮我找个赚钱的策略」。

**关键设计约束：**

- 信号机制只能从受约束 DSL 允许的集合中选择。允许集合由 DSL 版本决定，不由本文档枚举（§0.3）。无法用当前 DSL 表达的假设在预检阶段被拒，而不是退化成自由代码（上游 §8.2.1、§9.1）。
- **参数网格不由用户逐格填写。** 选定信号机制与市场档案即确定本轮的搜索空间与计划试验数。这是反 p-hacking 的结构性选择：用户能选检验什么，不能一格一格地喂参数直到通过（上游 §1、§6.2）。
- 「加载示例」只填输入，绝不创建任务、绝不产生 `FOUND`。

**状态：** 空表单 / 部分填写（冻结禁用）/ 校验失败（行内错误 + 汇总错误区）/ 已预检且未改动（冻结可用）/ 预检后被改动（冻结重新禁用，提示需重新预检）。

**边界：** 不提供自然语言直出策略代码；不提供自由 Python；不提供跨市场档案的混合研究（上游 §5.5）。

### 3.4 F4 验证方法配置（**新增**，核心）

**目标：** 让用户在研究开始前**看见并决定**「这一轮用什么标准判定成功」，并且这份决定与协议一起冻结、可审计、放宽留痕。

上游 §6.1 把「成功标准」列为冻结项，§9.3 规定只有确定性门槛评估器能产出 `FOUND`，但没有说这份预先声明如何被人看见和调整。这就是本功能补上的缺口。

#### 3.4.1 概念模型：验证点

**验证点（verification point）** 是本轮研究中一次可判定的检验。每个验证点有：

| 属性 | 取值 | 说明 |
| --- | --- | --- |
| 标识 | 稳定标识符 | 与 CLI、配置、证据文件共用同一个词 |
| `class` | `hard_gate` / `diagnostic` | 是否参与 `FOUND` 判定 |
| `scope` | 顶层 / 绑定 / 全轮 | 门槛本身 / 挂在某门槛下的子校验 / 对整轮提问的硬校验 |
| 归属 | 空或某个硬门槛标识 | 绑定范围必填 |
| 启用 | 是否本轮执行 | |
| 前置条件 | 样本量 / 数据源要求 | 决定是否会被 `skipped` |
| 参数 | 阈值等 | 数值由研究协议与引擎规格拥有（§0.3） |

`class` 只有两个取值，这两个取值的语义差别是产品的核心承诺：

- **硬门槛（hard_gate）**：全部到齐且全部通过 → `FOUND`。任一失败 → `NO_EVIDENCE`。任一缺席（含被跳过）→ `INCONCLUSIVE`（上游 §1、§6.3、§9.3）。
- **诊断项（diagnostic）**：结果被记录、被展示、可下钻，但**永不**决定 `FOUND`，也**永不**阻止 `FOUND`。诊断项被跳过只是少一条信息。

`scope` 描述这个检验问的是哪一层的问题，它不改变 `class` 的语义——一个绑定或全轮范围的检验若 `class` 为 `hard_gate`，它同样拥有否决权。

**绑定子校验** 挂在某个硬门槛上，让父门槛的判定更严：父门槛必须自身通过**且**其启用的绑定子校验全部通过。这一层存在的原因是现实——「样本外结果在各个市场状态下是否都站得住」不是独立结论，它就是「样本外是否站得住」的组成部分。界面上它们缩进在父门槛下面，而不是平铺成一堆同级选项。

**全轮硬校验** 对整轮而非某一门槛提问，例如收益的扣费口径、以及把全部试验计入后的多重检验计数（上游 §6.1、§6.2）。它们不属于任何单一门槛，界面上单独成一组显示在顶层门槛之后。

#### 3.4.2 验证点登记表的结构

**本文档定义登记表的结构与语义，不定义其条目清单与阈值**（§0.3）。权威清单由研究协议与引擎规格拥有；配置界面从那里读取，而不是硬编码一份副本。

登记表每一条必须提供，界面才能把它渲染成一个可理解的选项：

| 字段 | 界面用途 |
| --- | --- |
| 标识 + 一句人话释义 | 行首的「标识 — 人话」 |
| `class`、`scope`、归属 | 分组与缩进 |
| 判定条件（一句自然语言） | 释义第二行，让用户不查文档就懂在判什么 |
| 前置条件 | 可行性预判（§3.4.6）与 `skipped` 原因 |
| 默认来源 | 「来自市场档案」/「来自协议模板」标签 |
| 可否关闭、可否改类别 | 控件是否可用，以及禁用原因 |

上游已经点名的检验概念，可作为登记表在首版会包含的**示例**（不是完整清单）：

| 示例概念 | 上游依据 | 可能的 `scope` |
| --- | --- | --- |
| 去膨胀夏普（DSR）门槛 | §6.2「failure of DSR or another predeclared gate」 | 顶层硬门槛 |
| 样本外表现 | §3.3、§6.2「negative out-of-sample performance」 | 顶层硬门槛 |
| 与基准比较 | §3.3「excess returns」、§5.5「benchmark」 | 顶层硬门槛 |
| 数据质量与可用性检查 | §5.5「survivorship and availability checks」、§12 | 顶层硬门槛 |
| 市场状态稳定性 | §6.2「instability across required regimes」 | 绑定在样本外门槛下 |
| 扣除交易成本后的口径 | §6.2「failure after transaction costs」、§5.5 | 全轮硬校验 |
| 多重检验计数 | §6.1「included in the multiple-testing accounting」 | 全轮硬校验 |
| LLM 报告评审 | §9.3「LLM judge ... cannot override a gate」 | 诊断项，且**不可**升级为硬门槛 |

最后一行是唯一由上游直接固定 `class` 的条目：上游明确 LLM 评审不能覆盖门槛，因此它在登记表里只能是诊断项，界面上不提供升级控件。

#### 3.4.3 默认从哪来

默认验证清单 = **市场档案默认** ⊕ **协议模板默认**：

- **市场档案默认**给出该市场必须回答的问题。市场档案本身分别定义交易日历、数据集要求、基准、交易成本假设、流动性规则、存续与可用性检查（上游 §5.5），因此不同档案的默认清单可以不同——例如基准与成本相关的检验，在两个档案下的默认强度不必一致。
- **协议模板默认**由信号机制决定某些检验是否有意义，以及样本压力有多大。成型窗口长的机制会让依赖长样本的检验更容易被跳过，模板要在配置处直接标出这一点。
- 冲突时以市场档案为准，并显示来源标签，让用户知道默认不是随机的。
- 默认关闭需要额外数据源或额外资源的检验。默认开一个当前快照必然做不到的检验，会让绝大多数运行直接得出误导性的失败结论；想跑它的用户必须先准备条件，配置处要说明这一点。

首版支持 `us-equity-daily` 与 `crypto-daily` 两个独立档案（上游 §5.5）。两个档案的候选不放进一个默认排名；跨市场分析是可移植性检验，不是绝对绩效比较（上游 §5.5）。

#### 3.4.4 用户能改什么，不能改什么

| 操作 | 允许 | 规则 |
| --- | --- | --- |
| 关闭一个硬门槛 | 是 | 必须至少保留一个硬门槛 |
| 开启一个默认关闭的硬门槛 | 是 | 前置条件不满足时给出「必定跳过」预判 |
| 把某个硬门槛降级为诊断 | 是（登记表标记为可降级的条目） | 计入放宽留痕 |
| 把 LLM 报告评审升级为硬门槛 | 否 | 上游 §9.3 禁止；控件呈禁用态并给出原因 |
| 关闭扣费口径类的全轮硬校验 | 否 | 成本是结构性口径，不是可选检验（上游 §6.2） |
| 关闭绑定子校验 | 是（逐项） | 计入放宽留痕；父门槛关闭时整组随之隐藏 |
| 改阈值 | 否 | 阈值归研究协议与引擎规格（§0.3）。在产品界面放开阈值等于放开「调到通过为止」的后门（上游 §6.2） |
| 冻结后修改任何一项 | 否 | 属于经济性修订，进人工审核队列，需新的冻结协议（上游 §6.1） |
| 覆盖已产出的门槛结果 | 否 | 界面不存在任何覆盖控件（上游 §5.2、§9.3） |

**放宽留痕（relaxation trail）**

放宽 = 相对默认清单的任何削弱：关掉硬门槛、把硬门槛降级为诊断、关掉绑定子校验或可关闭的全轮硬校验。

- 配置处实时显示放宽项数，并列出每一项与原因输入（原因可空，空原因也会被记录为空）。
- 冻结确认处把放宽项单独成块，不与其它清单项混排。
- 结论页在主结论下方显示放宽徽标，可展开清单。
- `.asb` 血缘记录放宽清单，让下游能回答「这个结论是在什么标准下得到的」（上游 §8.2 的 lineage）。

**收紧不需要留痕**，因为它不会让结论变得更好看。

#### 3.4.5 关键 UI 元素

配置是提交区流程的一节（在假设与市场之后、预检之前），默认折叠为一行摘要，展开后是分组清单。下面是**结构示意**，条目为示例、阈值不在产品文档内断言（§0.3）：

```text
验证方法          硬门槛 3 · 全轮硬校验 2 · 诊断 1 · 放宽 1 · 计划 9 组参数

硬门槛（决定 FOUND）
  [x] 去膨胀夏普门槛                                  来自市场档案
      按本轮计划试验数去膨胀后须达到协议规定的置信水平
  [x] 样本外表现门槛                                  来自市场档案
      样本外收益须为正
      [x] 市场状态稳定性   各市场状态下均须为正
  [x] 与基准比较门槛                                  来自市场档案
  [ ] 数据质量与可用性检查                            必定跳过：未提供第二数据源

全轮硬校验
  [x] 扣除交易成本口径                                强制启用，不可关闭
      全部收益按市场档案的成本假设扣费后计算
  [x] 多重检验计数                                    来自协议模板

诊断项（不决定 FOUND）
  [x] LLM 报告评审                                    不可作为硬门槛
      结果会展示，但不会阻止 FOUND
```

必备元素：

1. **分组清单**：硬门槛组（绑定子校验缩进在父门槛下）、全轮硬校验组、诊断项组，三组视觉层级明确不同，且 F4、F10、F13 三处的分组与顺序完全一致。
2. **每项一行释义**：「标识 — 人话」，第二行是判定条件与前置条件。
3. **来源标签**：来自市场档案 / 来自协议模板。
4. **可行性预判徽标**（见 §3.4.6）。
5. **类别切换控件**：允许降级的项上出现「作为诊断运行」切换；不允许的呈禁用态并给出原因。
6. **放宽计数与清单**：始终可见，不藏在折叠里。
7. **试验计数联动**：清单变化不改变搜索空间，但去膨胀类门槛的强度取决于试验总数，配置处要说明这层联系（上游 §6.1）。
8. **恢复默认**：一键回到当前市场档案与协议模板的默认清单。

#### 3.4.6 可行性预判

配置处与预检共用一套判定，在**冻结之前**就告诉用户哪些验证点跑不成。输入是数据快照的覆盖范围、市场档案的日历与数据集要求、信号机制的成型窗口；输出三档：

| 预判 | 判定依据 | 界面 |
| --- | --- | --- |
| 可执行 | 前置条件按当前快照可满足 | 无徽标 |
| 可能跳过 | 处在边界，取决于运行期实际切分 | 中性徽标 + 原因 |
| 必定跳过 | 前置条件确定无法满足 | 告警徽标 + 原因 |

**这是本功能最重要的产品价值**：让「样本不够」在提交前暴露，而不是在结论页以 `INCONCLUSIVE` 的形式暴露。上游 §4.1 已要求预检覆盖数据、基准、成本、搜索空间与预算；本项把「判决标准本身是否可执行」也纳入同一次预检。

若清单里存在必定跳过的**硬门槛**，冻结确认处必须显著提示「按当前清单，本轮最好的结果是 `INCONCLUSIVE`」。用户仍可坚持冻结——研究者有权跑一次探路——但不能声称不知情。

#### 3.4.7 状态

| 状态 | 界面表现 |
| --- | --- |
| 未展开 | 一行摘要：硬门槛数 · 全轮硬校验数 · 诊断数 · 放宽数 · 计划参数组数 |
| 编辑中 | 清单可勾选；冻结禁用（任何编辑都要求重新预检） |
| 违反约束 | 行内错误，例如「必须至少保留一个硬门槛」 |
| 预检通过 | 清单只读预览态，显示可行性预判 |
| 已冻结 | 只读 + 协议指纹；提示「验证清单已随协议冻结」 |
| 运行中查看 | 只读，跳到 F10 验证进度 |

#### 3.4.8 边界

- 配置只回答「用什么标准判定」。它不改搜索空间，不改预算，不改假设。
- 不提供阈值输入。
- 不提供「本轮先不判定，跑完再决定」的模式——那等于取消预先声明（上游 §6.1）。
- 不提供自定义验证点（用户自带检验函数）。首版登记表是封闭的；扩展走 DSL 与登记表的版本升级，不走用户输入（上游 §8.2.1）。
- 不显示任何策略收益预测。

### 3.5 F5 预检与协议冻结

**目标：** 在正式运行前把「会失败的事」提前失败掉，并让用户在一份完整、可读的协议上按下不可反悔的冻结。

**入口：** 提交区的预检动作；CLI 等价操作（§3.17）。

**预检检查什么**（上游 §4.1、§9.1，加上 §3.4.6 的清单可行性）：

| 类别 | 检查项 | 失败表现 |
| --- | --- | --- |
| 假设可表达性 | 信号机制在受约束 DSL 内且可被解释 | 说明为什么不行，而不是退化成自由代码 |
| 市场档案 | 档案受支持、基准可用 | 拒绝 |
| 数据快照 | 快照存在、内容哈希匹配 | 区分「不可用」与「哈希不匹配」 |
| 成本假设 | 市场档案的成本假设完整 | 拒绝 |
| 搜索空间 | 搜索空间与计划试验数可确定 | 拒绝 |
| 验证清单 | 至少一个硬门槛；类别约束合法 | 拒绝并指向配置处 |
| 清单可行性 | 逐验证点给出可执行 / 可能跳过 / 必定跳过 | 不拒绝，但必须展示 |
| 预算 | 时间与成本预算合法 | 拒绝 |
| 资源 | 磁盘空间、目录可写、计算资源 | 拒绝 |
| 主机约束 | 输出运行期披露三句 | 始终展示 |

**协议预览展示什么：**

- 计划试验数（醒目呈现，这是多重检验的规模，用户有权在冻结前知道）。
- 假设陈述、信号机制释义、市场档案释义、基准。
- 验证清单摘要与逐项可行性预判。
- 随机种子、时间预算、成本预算。
- 数据快照 ID 与哈希。
- 搜索空间的可读呈现：一行一组参数，而不是一坨结构化文本。人读不懂的披露不算披露。

**冻结动作：**

- 冻结按钮默认禁用，仅在「预检成功」且「预检之后未再改动任何输入」时可用。改一个字就重新禁用。这是本产品最重要的一条交互纪律：**冻结的必须是用户刚刚看过的那份协议**。
- 冻结把上游 §6.1 的冻结集合（经济逻辑、信号机制、市场范围、基准、成功标准）连同数据快照引用、预算、随机种子与**验证清单**一并写入冻结协议文档，并由覆盖全部内容的哈希（协议指纹）固定。字段布局与字段名归运行时规格（§0.3）。
- 冻结后立即返回 `run_id`（上游 §4.1），界面定位到该任务。

**状态：** 未预检 / 预检中 / 预检失败（错误列表）/ 预检通过（冻结可用）/ 预检通过后被改动（冻结再次禁用）/ 已冻结（返回 `run_id`）。

**边界：** 预检错误**不是**研究结论（上游 §9.1）。被预检拒绝的运行不产生 `run_id`，不进任务列表，不产生任何结论。预检本身不创建任务、不产生 `FOUND`。

### 3.6 F6 任务控制：提交、取消、断点续跑

**目标：** 让用户相信「我不在的时候发生的事，我能控制，也能理解」。

**入口：** 任务详情动作区；CLI 等价操作。控制面负责创建、取消、续跑与查询任务，并强制预算与运行状态机（上游 §5.1）。

**关键动作与可见条件：**

| 动作 | 可见条件 | 效果 |
| --- | --- | --- |
| 提交（冻结） | 预检通过且未改动 | 创建任务，立即返回 `run_id` |
| 取消 | 状态为 `queued` 或 `running` | 终止 worker，任务转 `cancelled` |
| 续跑 | 状态为 `failed` | 重新入队，从最近一个完整 checkpoint 继续（上游 §9.2） |
| 重放结论 | 始终 | 由已封存证据重新生成报告，不重跑研究（上游 §7） |

**必须披露的三句话**（上游 §4.1，在预检结果与帮助处措辞一致）：

1. 本机 worker 运行期间，主机必须保持唤醒。
2. 关闭浏览器或终端**不会**停止任务。
3. 挂起或关机**会**停止计算。

第一与第三句是「长时间自主研究」的真实代价，必须在提交前说清楚，而不是在用户回来后用一句「进度停了」来解释。上游把用户自有云端 worker 列为未来选项，用于无法让主机长时间保持唤醒的场景（上游 §4.1）。

**恢复语义：**

- 心跳超期或 worker 进程消失 → 控制面终止残留进程、记恢复尝试、重新拉起，从最近一个完整 checkpoint 续跑（上游 §5.1、§5.3、§9.2）。
- 恢复尝试用尽 → 任务转 `failed`，研究结论为 `INCONCLUSIVE`（上游 §5.3、§9.2）。
- 已封存的 `FOUND` 不会因为后续技术故障被抹掉（上游 §6.3）。

**状态：** 任务状态与研究结论**分两行显示，永不合并**。「任务状态：运行中」与「结论：尚未终结」同屏出现不构成矛盾——前者说进程，后者说证据（上游 §6.3）。

**边界：** 不提供暂停 / 恢复（只有取消与续跑）；不提供优先级与队列重排；不提供修改运行中任务的协议。

### 3.7 F7 进度总览

**目标：** 用户扫一眼就知道「跑到哪了、还剩多少、活着吗」。这是长时间运行必须提供的确定感。

**入口：** 任务详情上部，运行中与终态共用。

**关键 UI 元素：**

| 元素 | 内容 |
| --- | --- |
| 搜索进度 | 已试验数 / 计划试验数 + 进度条 |
| 预算 | 时间与成本预算，以及已消耗与剩余（上游 §5.1 强制预算） |
| 检查点 | 最近一个完整 checkpoint 的标识与时间 |
| 心跳 | worker 最近心跳时间 |
| 恢复 | 恢复尝试次数（> 0 时） |
| 错误 | worker 错误信息（有则显示） |

**状态：** 排队中（进度 0，显示「等待 worker」）/ 运行中（进度推进，心跳刷新）/ 恢复中（进度可能回退到 checkpoint 处，必须明说「已从检查点续跑」）/ 终态（进度冻结在最终值）。

**边界：** **禁止假进度。** 进度只反映真实完成的试验数与真实检查点推进，不做时间插值动画。**不显示预测性剩余时间倒计时**——研究时长取决于证据与停止规则，编一个倒计时是在承诺产品无法保证的事。只显示预算余量。

### 3.8 F8 试验台账（trial ledger）

**目标：** 任何一条结论都能被追到「具体哪次试验、什么参数、算出了什么」。

**入口：** 任务详情底部，默认折叠。

**关键 UI 元素：** 只读表格，一行一次试验：

| 列 | 内容 |
| --- | --- |
| 试验标识 | 等宽 |
| 信号机制 | 标识 — 人话 |
| 参数 | 可读的键值呈现 |
| 修订类别 | 无 / 方法性（§3.14） |
| 验证结果摘要 | 通过数 / 需要数，失败项高亮（**新增**） |
| 下钻 | 展开该候选的策略验证结果（F13） |

页脚固定说明：台账是运行产物中 trial ledger 的视图；每条记录都计入多重检验计数（上游 §4.2、§6.1）。

**状态：** 空（尚无试验）/ 增量填充（运行中持续追加，不重排已有行）/ 完整（终态）/ 部分不可解析（跳过该行并显示不可解析的行数，不整表报错）。

**边界：** 台账只读、只增。界面不提供删除、编辑、隐藏某次试验的能力——那会破坏多重检验计数的完整性（上游 §6.1、§12）。

### 3.9 F9 候选漏斗

**目标：** 回答「为什么这一轮没有东西入围」，并把答案变成下一次的行动依据（上游 §4.3）。

**入口：** 任务详情，证据摘要下方。

**关键 UI 元素：**

- 汇总行：已评估 / 通过 / 未通过 / 证据不完整。
- 堆叠条：三段配色与三结论体系一致。
- 主因列表：按失败次数降序的门槛，「门槛释义 × 次数」，配比例条（上游 §4.3 的 dominant failure reasons）。
- 每个主因可展开到受影响的候选列表。

**状态：** 空 / 部分（运行中随试验推进更新）/ 完整（终态）。

**边界：** 漏斗**只读**。界面不提供「放行这个候选」「忽略这一关」的操作——证据门槛不可在界面被覆盖（上游 §5.2、§9.3）。

### 3.10 F10 验证进度（**新增**）

**目标：** 运行中就能看见「验证清单跑到哪一项了」，而不是等终态才知道结果。对一个会跑数小时的任务，这是把黑箱变成可观测过程的关键一屏。

**入口：** 任务详情，进度总览下方；运行中默认展开，终态自动收起为 F13 的入口。

**关键 UI 元素：** 与 F4 的配置清单**同构**（同样的分组、缩进、释义），只是把选择控件换成状态徽标：

```text
验证进度                          硬性检验 已完成 3 / 5 · 当前候选 #4

硬门槛
  去膨胀夏普门槛      pass        达到协议规定的置信水平
  样本外表现门槛      incomplete  自身样本外收益为正，但市场状态稳定性被跳过
    市场状态稳定性    skipped     样本不足
  与基准比较门槛      running
全轮硬校验
  扣除交易成本口径    pass        已按市场档案成本假设扣费
  多重检验计数        pending
诊断项
  LLM 报告评审        pending     不影响 FOUND
```

完成度计数器只数**有否决权的**验证点，即顶层硬门槛加全轮硬校验。绑定子校验随父门槛计入，诊断项不计入——否则一个诊断项跑完会让用户误以为结论更近了一步。

**逐验证点状态：**

| 状态 | 含义 | 视觉 |
| --- | --- | --- |
| `pending` | 已在清单中，尚未执行 | 中性 |
| `running` | 正在执行 | 活动指示 |
| `pass` | 通过 | 通过标识 |
| `fail` | 未通过 | 告警标识 |
| `skipped` | 前置条件不满足，未能执行 | 告警标识 + 必须带原因 |
| `incomplete` | 自身有结果，但其启用的绑定子校验被跳过，因此不计为通过 | 未定标识 + 必须说明是哪一项 |
| 未启用 | 冻结时未选入清单 | 不出现在进度里（可切换查看） |

`incomplete` 是本设计新增的一等状态。它存在的唯一理由是：一个门槛「自己算出来是正的、但少了一项该做的检验」既不是通过也不是失败，界面必须能把这件事说清楚，而不是被迫二选一。

**`skipped` 的结论语义：**

| 被跳过的对象 | 对结论的影响 |
| --- | --- |
| 硬门槛 | 该门槛在证据集中缺席 → 证据不完整 → `INCONCLUSIVE`。**绝不当作通过。** |
| 绑定子校验 | 父门槛转为 `incomplete`，不得仅凭自身通过而计为 `pass` → `INCONCLUSIVE` |
| 全轮硬校验 | 本轮证据不完整 → `INCONCLUSIVE` |
| 诊断项 | 仅记录，不影响结论 |

这直接落实上游 §9.3：缺失、损坏或不完整的证据阻止 `FOUND`，缺失的诊断不能产出 `FOUND`。要求是**把缺席显式化**——能被表达，才能被降级。悄悄少算一项然后给出乐观结论，是本产品最不能犯的错误。

**跳过原因**必须与状态同时呈现，且以人话表述（例如「样本不足」「缺少第二数据源」「缺少基准序列」「引擎错误」），不直接暴露内部标识符。

**状态：** 排队中（全部 `pending`）/ 运行中（逐项推进，按候选切换）/ 终态（定格）/ 无数据（尚未产出任何门槛结果时显示清单与全 `pending`，不显示空白）。

**边界：** 验证进度是观测面板，没有任何控件能改变清单或结果。运行中不允许增删验证点。

### 3.11 F11 结论页：唯一主结论

**目标：** 几分钟读懂。第一屏只需回答一个问题：**这一轮的结论是什么。** 上游 §3.4 把「用户能在五分钟内识别结论、主要证据与停止原因」列为首版成功标准。

**入口：** 任务列表选中任一任务；CLI 等价查询。

**关键 UI 元素（自上而下，顺序固定）：**

1. **主结论**：`FOUND` / `NO_EVIDENCE` / `INCONCLUSIVE` 单词，最大字号，独立视觉标识。
2. **一句解释**：见 §5.2 的语义要求。
3. **主要证据**：`FOUND` 时为「所有必需硬门槛均通过」；`NO_EVIDENCE` 时点名未通过的门槛；`INCONCLUSIVE` 时点名缺失或未完成的门槛。
4. **停止原因**：全门槛通过 / 门槛未通过 / 证据不完整 / 预算耗尽；非终态显示「运行中或尚未终结」。
5. **放宽徽标**（**新增**）：本轮放宽项数，可展开；为零时不显示。
6. **任务状态区**：任务状态、心跳、恢复尝试、worker 错误，与结论视觉分离。

**状态：**

| 状态 | 主结论区表现 |
| --- | --- |
| `queued` / `running` | 结论区显示尚未终结，并说明「任务状态不是研究结论」；主要证据与停止原因显示「运行中或尚未终结」 |
| `completed` + 全门槛通过 | `FOUND` |
| `completed` + 证据完整但有失败 | `NO_EVIDENCE` |
| `completed` + 证据不完整 | `INCONCLUSIVE` |
| `failed` / `cancelled` | `INCONCLUSIVE`，除非已有更早封存的 `FOUND` |
| 无任何任务 | 空态引导 + 不承诺 alpha 声明 |

**边界：** 一次运行只有一个主结论，不出现「部分成功」「接近通过」「置信度 87%」等中间态措辞。不以收益曲线作为视觉主体——结论页的中心是判决，不是业绩展示。结论页不按提交或结束的时刻组织内容。

### 3.12 F12 证据摘要

**目标：** 让主结论可被检验，而不是被相信。

**入口：** 结论页主结论下方。

**关键 UI 元素：** 每个必需门槛一行：「门槛释义：通过 / 未通过 · 关键指标 = 值 · …」。

关键指标按门槛类型选取，并且**必须带口径**：收益是样本外还是全样本、是否已扣费、计入了多少次试验。上游 §5.2 要求 Web 控制台支持证据检视，§7 规定报告是证据的视图而不是来源——因此每行都可展开到运行产物证据目录中的原始输入引用，并附一句「报告是证据的视图，不是证据的来源」。

**状态：** 无已封存证据（说明这会导致 `INCONCLUSIVE`）/ 部分（运行中）/ 完整（终态）。

**边界：** 证据摘要不做跨运行对比，不做排行榜。不同市场档案的候选不进同一个默认排名（上游 §5.5）。

### 3.13 F13 策略验证结果（**新增**，核心）

**目标：** 对每一个候选策略——入围的和被淘汰的——回答「它在我选的每一项验证上表现如何」，并且每一条都能下钻到证据。

这是 F4 的对偶：F4 让用户在开始前**选**验证方法，F13 让用户在结束后**按同一份清单读**结果。两者的分组、顺序、释义完全一致，用户不需要建立两套心智模型。上游 §4.3 要求结论之后呈现入围候选与支撑证据；本功能规定这份呈现按验证点组织。

**入口：** 两处，同一组件：

1. **结论页**：入围候选列表中每一行可展开为验证结果面板。
2. **策略详情**：从入围候选、候选漏斗主因、试验台账任意一处点进的候选详情面板（同一 `run_id` 内的面内下钻）。

**关键 UI 元素（结构示意，条目为示例）：**

入围候选：

```text
候选 #4 · 12-1 动量 · 参数：回看窗口 12 个月 · 跳过窗口 1 个月
状态：入围（所有必需硬门槛通过）              导出 .asb

硬门槛                    结果        关键指标                     证据
  去膨胀夏普门槛          pass        达到协议置信水平 · 计入 9 次试验   证据目录
  样本外表现门槛          pass        样本外收益为正（已扣费）          证据目录
    市场状态稳定性        pass        各市场状态下均为正
  与基准比较门槛          pass        样本外超额为正
全轮硬校验
  扣除交易成本口径        pass        已按市场档案成本假设扣费
  多重检验计数            pass        已计入全部试验与方法性修订
诊断项（不决定结论）
  LLM 报告评审            pass        放宽：不参与门槛判定

本轮放宽 1 项：某硬门槛已降级为诊断。
该结果不构成 alpha 或未来盈利的承诺。
```

淘汰候选与证据不完整候选用同一套结构，只是结果列不同，并把首个需要注意的行置顶高亮：

```text
候选 #2 · 状态：淘汰（样本外表现门槛未通过）
  样本外表现门槛          fail        样本外收益为负            ← 首个失败
  去膨胀夏普门槛          pass

候选 #7 · 状态：证据不完整（市场状态稳定性被跳过）— 这不是「几乎通过」
  样本外表现门槛          incomplete  自身为正，但子校验被跳过   ← 需注意
    市场状态稳定性        skipped     样本不足
```

必备元素：

1. **候选身份行**：试验标识 · 信号机制释义 · 参数。
2. **候选状态**：入围 / 淘汰（附首个失败门槛）/ 证据不完整（附缺失项）。
3. **逐验证点表**：分组与缩进与 F4、F10 完全一致；列为结果 / 关键指标 / 证据链接。
4. **证据下钻**：指向运行产物证据目录中该候选的记录。
5. **放宽提示**：若本轮有放宽，在候选面板底部重复一次——用户可能直接从台账跳进来，没看过结论页顶部。
6. **导出入口**：仅当研究结论为 `FOUND` 且该候选在已封存证据中时出现（上游 §8.2）。
7. **反夸大声明**：面板底部固定一句。

**淘汰候选也要展示。** 这是刻意的设计：研究的价值经常在于「它死在哪一关」，而这正是上游 §4.3 要求呈现淘汰漏斗与主因的原因。

**状态：**

| 状态 | 表现 |
| --- | --- |
| 无候选 | 空态，并说明可能原因（无试验完成 / 全部证据不完整） |
| 运行中的候选 | 已完成的验证点显示结果，未完成显示 `pending`，不显示半成品指标 |
| 入围 | 全部必需硬门槛通过 |
| 淘汰 | 至少一项必需硬门槛未通过 |
| 证据不完整 | 至少一项必需硬门槛为 `skipped`、`incomplete` 或缺席；明确说明这不是「几乎通过」 |

**边界：** 面板只读。不提供「重跑这个候选」「把这个候选标记为通过」的操作。不显示未来收益预测、不显示建议仓位、不显示任何交易相关字段（上游 §9.4）。

### 3.14 F14 方法修订复盘

**目标：** 让用户知道「运行期这台机器替我改了什么」，并确认它没有偷偷改掉假设。

**入口：** 结论页，候选漏斗下方（上游 §4.3 要求呈现运行期的方法性修订）。

**关键 UI 元素：** 每行「试验标识 · 修订类别 · 信号机制释义 · 参数」。修订类别只有两种（上游 §6.1）：

| 类别 | 含义 | 是否允许在本轮执行 |
| --- | --- | --- |
| 方法性修订 | 数据不完整或无效、实现细节含糊、成本假设缺失、参数覆盖不足但相关、可恢复的实验实现错误 | 允许，且必须计入多重检验计数 |
| 经济性修订 | 经济逻辑、信号机制、市场范围、成功标准（含**验证清单**）的改变 | **不允许**，转入下一假设队列 |

**验证清单的变更属于经济性修订。** 上游 §6.1 把「成功标准」列入冻结集合，并规定改变它构成新假设、需要人工批准。界面必须把这一点讲明白，否则用户会以为「只是调了个检验项」。

**状态：** 空（说明本轮未发生方法性修订）/ 有修订（列表）/ 有经济性修订被排队（指向 F15）。

**边界：** 复盘只读。不提供「撤销这次修订」。

### 3.15 F15 下一假设建议队列

**目标：** 把「这次学到了什么」变成下一次的起点，同时严守「新经济假设绝不在同一次运行里静默执行」（上游 §4.3、§6.1）。

**入口：** 结论页下部。`FOUND` 与 `NO_EVIDENCE` 都可能产生建议——没有证据同样有信息量。

**关键 UI 元素：**

- 建议列表：每条一句假设陈述 + 排队原因（以人话表述）。
- 「载入编辑器」：把建议填回 F3 输入并**自动触发一次协议预检**，用户看到的是一份完整的新协议，而不是一段文本。
- 「下一步」提示：结论页顶部附近显示第一条建议，作为明确的下一步动作。

**关键约束：** 载入建议 = 新研究。它会得到新的协议指纹、新的 `run_id`、新一轮验证方法配置（默认继承上一轮清单，包括放宽项，并显式提示「继承自上一轮，含 N 项放宽」）。它**不会**复用上一轮的证据，也**不会**自动提交——新假设需要人工批准（上游 §6.1）。

**状态：** 空 / 有建议（列表 + 下一步提示）/ 已载入（输入被填充，冻结因「尚未预检通过」保持禁用直至预检完成）。

**边界：** 建议**只是建议**。产品不排序建议的「胜率」，不预测建议的收益，不自动执行任何一条。

### 3.16 F16 .asb 导出与交接

**目标：** 把一个 `FOUND` 候选变成不可变、可校验、自带血缘的数据包，交给 AlphaStrategy；并在这一步把边界说清楚。

**入口：** 结论页交接区（仅 `FOUND`）、候选验证结果面板、以及上游 §8.2 给出的命令形式：

```text
alphaloop export <candidate_id> --output strategy.asb
```

**关键 UI 元素：**

- 交接区：入围候选标识 · 信号机制释义 · 参数，加导出动作。
- 导出回执：结论词、入围候选、导出路径，以及固定的「本次导出不构成 alpha 或未来盈利的承诺」。
- 内容说明（可展开）：包内含 schema 版本、规范内容哈希与由其派生的内容寻址包标识、受约束策略 DSL、冻结参数与市场档案、研究阶段风险假设、完整运行与证据血缘、固定的一致性校验输入与预期输出、可选的注册表地址；**不含**凭据，**不含**任何可执行文件（上游 §8.2、§8.2.1）。
- 放宽清单（**新增**）：血缘中记录本轮验证清单与放宽项；回执提示「本包的结论是在放宽 N 项的标准下得到的」。

**状态：** 不可导出（非 `FOUND` 时不出现；CLI 明确拒绝并说明需要 `FOUND`）/ 可导出 / 导出中 / 成功（回执）/ 失败（候选不在已封存证据中、路径不可写等，逐条说明）。

**边界（硬墙）：** 导出是一次**人工动作**，不自动触发（上游 §8.2）。alphaloop 不持有券商凭据、不连接券商、不提交模拟或实盘订单、不调用 AlphaStrategy 执行接口、不自动晋级候选（上游 §9.4）。集成单向：alphaloop → `.asb` → AlphaStrategy，没有回传遥测（上游 §8.1）。导入不等于授权交易；晋级到模拟、影子或实盘是 AlphaStrategy 侧独立的人工审批流程（上游 §8.4）。

### 3.17 F17 次要入口：CLI 与 Agent Skill

**目标：** 服务已经在用编码 agent 的用户，但不把主路径搬到命令行。上游 §10.1 明确 Web 控制台是主要界面，因为它承载长任务、进度、复盘与产物导航。

**CLI 覆盖的能力**（上游 §5.1、§10.2；子命令与参数的完整表归 CLI 规格，§0.3）：

| 能力 | 说明 |
| --- | --- |
| 启动本机控制面 | `alphaloop start`（上游 §5.1） |
| 提交任务 | 长任务返回 `run_id`，不占着一个同步会话不放（上游 §10.2） |
| 查询状态与结论 | 结论、主要证据、停止原因、漏斗、验证清单结果 |
| 取消与续跑 | 与控制面同一套任务生命周期（上游 §5.1） |
| 重放结论 | 由已封存证据重生成报告 |
| 导出候选包 | `alphaloop export <candidate_id> --output strategy.asb`（上游 §8.2） |

CLI 输出遵循与界面相同的结论优先顺序：结论词 → 一句解释 → 主要证据 → 停止原因 → 漏斗 → 修订 → 下一步 → 入围候选 → 任务状态 → 不承诺 alpha 声明。

**Agent Skill**（上游 §10.3 逐条列出）：教编码 agent 构造并预检假设、通过 CLI 或 Job API 提交、**轮询而不是阻塞数小时**、正确解释三种结论、在门槛失败后不宣称 alpha、在需要新假设或导出候选包时请求人工批准。Skill 是工作流指引，不是服务，也不是证据引擎。

**边界：** 首版不含 MCP 适配器。未来的 MCP 只做短异步操作（创建运行、查状态、取结果、取消），**任何 MCP 调用都不得为一次长时间运行保持打开**（上游 §10.4）。桌面壳延后：本机控制面加打包 Web 控制台已能提供所需体验（上游 §10.5）。

## 4. 流程

### 4.1 主流程

```text
[F1] 启动本机控制面            alphaloop start → 控制面可接单
        │
[F3] 定义研究（随时）          假设 + 市场档案 + 数据快照 + 预算
        │
[F4] 配置验证方法              默认清单（市场档案 ⊕ 协议模板）→ 用户调整 → 放宽留痕
        │
[F5] 预检                      可表达性 / 数据 / 成本 / 搜索空间 / 清单合法性与可行性 /
        │                      预算 / 资源 / 运行期披露三句
        │                      ├─ 失败 → 回到 F3 或 F4（不产生 run_id）
        │                      └─ 通过 → 协议预览（含验证清单终确认）
        │
[F5] 冻结                      冻结协议 + 协议指纹（覆盖验证清单）→ 立即返回 run_id
        │
[F6] 长时间自主运行            worker 独立于浏览器与提交 shell；checkpoint 持续写入；
        │                      预算与停止规则约束时长
        │
[F7/F8/F9/F10] 观测（可选）    进度 / 台账 / 漏斗 / 逐验证点状态
        │                      用户可以中途看，也可以完全不看
        │
        │                      停止：全门槛通过 · 门槛未通过且搜索空间耗尽 ·
        │                      预算耗尽 · 经济性修订被排队
        │
[F11] 结论（回来时）           FOUND / NO_EVIDENCE / INCONCLUSIVE（唯一主结论）
        │
[F12/F13/F14] 复盘             证据摘要 / 每候选逐验证点结果 / 方法修订
        │
        ├─[F16] FOUND → 人工导出 .asb → AlphaStrategy（单向，导入不等于授权交易）
        └─[F15] 任意结论 → 下一假设建议 → 载入编辑器 → 新协议指纹的下一轮
```

流程对时刻不敏感。用户可以提交后立刻盯着看，也可以关掉浏览器隔很久再回来；两者走的是同一条路径，界面不因此改变结构。

### 4.2 停止规则：为什么运行会结束

「长时间自主研究」必须有明确的终止条件，否则就变成「跑到通过为止」。上游 §6.2 规定研究可以在预算内继续，但**只在下一次实验能可信地增加证据时**继续。

以下情况**不构成**继续参数搜索的理由，界面在展示停止原因时必须如实呈现：

- 样本外表现为负；
- 扣除交易成本后失败；
- 去膨胀夏普或其它预先声明的门槛未通过；
- 在要求的市场状态下不稳定；
- 只有扩大一个已经失败的参数搜索才能改善。

这条规则是产品可信度的来源之一，也是「自主」不等于「无限」的边界。

### 4.3 异常流程

| # | 异常 | 触发 | 产品行为 | 结论影响 |
| --- | --- | --- | --- | --- |
| E1 | 假设无法用受约束 DSL 表达 | 预检 | 拒绝并说明原因，不退化为自由代码 | 无 `run_id`，无结论 |
| E2 | 数据快照缺失或哈希不符 | 预检 / 重放 | 拒绝，区分「不可用」与「哈希不匹配」；重放**失败关闭**，不用近似数据凑 | 无结论 / 重放失败 |
| E3 | 缺少基准 | 预检 | 拒绝 | 无 `run_id` |
| E4 | 验证清单不合法 | 预检 | 拒绝并指向配置处，高亮违规项 | 无 `run_id` |
| E5 | 清单含必定跳过的硬门槛 | 预检 | **不拒绝**，但冻结确认处显著提示「本轮最好的结果是 `INCONCLUSIVE`」 | 用户坚持则最终 `INCONCLUSIVE` |
| E6 | 资源不足（磁盘 / 计算 / 预算） | 预检 | 拒绝并给出具体缺口 | 无 `run_id` |
| E7 | 单个候选计算失败 | 运行中 | 隔离，淘汰该候选，其余继续；台账记录 | 不影响整轮 |
| E8 | 验证点前置条件不满足 | 运行中 | 标记 `skipped` + 原因；硬门槛、其绑定子校验或全轮硬校验被跳过则证据不完整 | `INCONCLUSIVE` |
| E9 | 数据完整性或诊断引擎故障 | 运行中 | 停止整轮，记录错误 | `INCONCLUSIVE` |
| E10 | worker 崩溃（可恢复） | 运行中 | 终止残留 → 记恢复尝试 → 从最近完整 checkpoint 续跑 | 不影响结论 |
| E11 | worker 不可恢复 | 运行中 | 任务转 `failed`，显示 worker 错误与恢复尝试，提供续跑 | `INCONCLUSIVE` |
| E12 | 主机挂起 / 关机 | 运行中 | 计算停止（已在预检披露）；恢复供电后由续跑从 checkpoint 继续 | 续跑成功则不影响 |
| E13 | 时间或成本预算耗尽 | 运行中 | 正常停止，停止原因为预算耗尽 | 必需证据不完整时 `INCONCLUSIVE` |
| E14 | 门槛未通过且搜索空间耗尽 | 运行中 | 停止搜索，**不扩大已失败的搜索空间**（§4.2） | `NO_EVIDENCE` |
| E15 | 全轮硬校验在结论生成时刻未通过 | 结论生成 | 例如把全部试验与方法性修订计入多重检验后，去膨胀类门槛不再成立：不得给出 `FOUND`，证据行写明口径 | 降级为 `NO_EVIDENCE` |
| E16 | 提出经济性修订（含改验证清单） | 运行中 | 停止本轮搜索，转入下一假设队列，等人工审核 | 按已有证据定结论 |
| E17 | 用户取消 | 运行中 | 终止 worker，任务转 `cancelled` | `INCONCLUSIVE`（除非已有更早封存的 `FOUND`） |
| E18 | 对非 `FOUND` 请求导出 | 导出 | 拒绝并说明需要 `FOUND` | 无 |
| E19 | 导出候选不在已封存证据中 | 导出 | 拒绝并说明该候选未在封存证据里 | 无 |
| E20 | 台账某行不可解析 | 展示 | 跳过该行，显示不可解析的行数，其余照常渲染 | 无 |
| E21 | 控制面未运行 | 任意 | 页面不可达；CLI 提示先启动控制面 | 无 |

**贯穿所有异常的两条纪律：**

1. **失败关闭。** 缺失、损坏、部分的证据一律不能产出 `FOUND`；只能是 `INCONCLUSIVE`（上游 §9.3）。
2. **技术故障不是研究结论。** worker 崩溃说明这台机器出了问题，不说明假设不成立。界面必须让这两件事在不同的行里（上游 §6.3）。

### 4.4 状态机

**任务状态**（进程视角，上游 §6.3）：

```text
queued ──> running ──> completed
             │  ├────> failed ──(续跑)──> queued
             │  └────> cancelled
             └──(心跳超期 / 进程消失，记恢复尝试)──> running
```

**研究结论**（证据视角，上游 §6.3）：

| 任务状态 | 证据完整 | 全门槛通过 | 结论 |
| --- | --- | --- | --- |
| `queued` / `running` | — | — | 尚未终结 |
| `completed` | 是 | 是 | `FOUND` |
| `completed` | 是 | 否 | `NO_EVIDENCE` |
| `completed` | 否 | — | `INCONCLUSIVE` |
| `failed` / `cancelled` | — | — | `INCONCLUSIVE`（除非已有更早封存的 `FOUND`） |

`failed` 或 `cancelled` 的任务**不能**声称 `FOUND`。

## 5. 交互原则与文案规则

### 5.1 五条交互原则

**原则一：结论优先。** 任何展示研究结果的界面（结论页、CLI 输出、报告、导出回执）都以结论词开头，其余按 §2.4 的固定顺序往下沉。不允许因为某段内容更丰富就把它提到结论之前。

**原则二：识别优于回忆。** 用户应当看到可选的信号机制、市场档案、验证点，而不是记住配置键名与门槛标识符。每个标识符旁边都有「标识 — 人话」释义。

**原则三：判决标准先于结果。** 判定成功的标准必须在研究开始前被看见并冻结。冻结之后不能改标准，也不能在界面上覆盖已产出的门槛结果。界面里不存在覆盖控件（上游 §5.2、§6.1、§9.3）。

**原则四：诚实的进度。** 不做假进度，不做预测性剩余时间倒计时。动效只用于真实的检查点推进与面板展开，并尊重系统的减少动态效果设置。所有运行状态在静止时都应可读——用户回来时看的是一屏静态信息，不是一段动画。

**原则五：一处放宽，处处可见。** 相对默认标准的任何削弱都在配置处、冻结确认处、结论页与 `.asb` 血缘四处出现。产品允许用户放宽，不允许放宽被隐藏。

### 5.2 三结论语义与解释文案

三个结论词在任何界面上都以英文原词呈现（`FOUND` / `NO_EVIDENCE` / `INCONCLUSIVE`），视觉标识互不相同，并各配一句解释。每句解释必须同时包含**判定条件**与**反夸大声明**：

| 结论 | 判定条件（上游 §1、§6.3） | 解释句必须同时说明 |
| --- | --- | --- |
| `FOUND` | 至少一个候选通过了每一项预先声明的硬门槛，且证据完整 | 这不是 alpha 的承诺 |
| `NO_EVIDENCE` | 研究完成，但证据不支持已冻结的假设 | 这不代表已证明 alpha 不存在 |
| `INCONCLUSIVE` | 数据、预算、诊断或技术故障使有效结论无法成立 | 缺失的诊断不能产出 `FOUND` |
| 尚未终结 | 任务处于排队或运行中 | 任务状态不是研究结论 |

三条推论，界面必须体现：

1. `NO_EVIDENCE` **不是**失败态。它是一个信息量充足的结论，有独立视觉标识、有下一步建议、可以产生下一假设。不用错误色，不用「失败」「错误」措辞。
2. `INCONCLUSIVE` **不是**「差一点通过」。它表示「不知道」。界面禁止出现「接近通过」「仅缺一项即可通过」这类暗示。
3. 缺失的诊断**不能**产出 `FOUND`。这是产品最重要的安全承诺，也是 `skipped` 必须降级结论的原因（上游 §9.3）。

### 5.3 文案规则

**必须做：**

- 门槛、信号机制、市场档案、跳过原因一律「标识 — 人话」双写。标识符与 CLI、配置、证据文件保持同一个词，便于对照。
- 每个展示结论或导出结果的界面都带一句反夸大声明。
- 任务状态与研究结论分行，永不合并成一个身份串。
- 数字带口径。写「样本外平均夏普（已扣费）」而不是「夏普」；写「按 9 次试验去膨胀后达到置信水平」而不是「通过」。
- 时间用**时长与事件**表述，不用时段。写「已运行 3 小时 12 分」「已完成 6 / 9 组试验」「最近检查点 12 分钟前」，不写「跑了一夜」。

**禁止做**（适用于界面、CLI 输出、报告与导出回执）：

| 类别 | 禁止出现 |
| --- | --- |
| 交易暗示 | 买入、卖出、开仓、仓位建议、止损、下单、实盘、模拟盘、上线、部署、晋级 |
| 收益承诺 | 预期收益、年化回报预测、胜率、盈利概率、发现 alpha、稳定赚钱 |
| 夸大与暗示 | 接近通过、几乎通过、大概率有效、值得一试、推荐使用 |
| 拟人化权威 | AI 认为可以、模型建议买入、智能推荐 |
| 界面能力 | 覆盖门槛、强制通过、忽略此门槛、标记为通过 |
| 社交与竞技 | 排行榜、收益榜、跟单、分享战绩 |
| 时段化叙事 | 睡前提交、隔夜运行、第二天早上、早间结论、早晨首页 |

最后一类是本版新增的禁用类别。产品不假设用户的作息：一个下午提交、傍晚回来读结论的用户，不应该在一个以睡眠周期命名的地方找他的结论。功能与文案一律用「随时提交 / 长时间运行 / 回来读结论」的措辞。

**语言选择：** 本设计文档用中文书写，产品术语保留英文原词：`FOUND`、`NO_EVIDENCE`、`INCONCLUSIVE`、`run_id`、`.asb`、`checkpoint`、`trial ledger`、`hard gate`、`DSR`。这些词是用户与 CLI、配置、证据文件之间的共同词汇，翻译反而增加对照成本。界面文案的语言与本地化不在首版范围（§6.2）。

### 5.4 视觉语义

配色与形状承载语义，不承载装饰。本文档规定**语义要求**，不规定具体色值（色值归界面实现规格，§0.3）：

| 语义 | 要求 |
| --- | --- |
| `FOUND` | 专用的通过标识，且**必须**与「证据集完整」同时出现，不允许在证据不完整时以任何形式出现 |
| `NO_EVIDENCE` | 独立标识，不得与 `FOUND` 共用，也不得使用表示技术错误的样式 |
| `INCONCLUSIVE` | 独立的「未定」标识，不得与 `NO_EVIDENCE` 混同 |
| 验证点 `incomplete` | 与 `INCONCLUSIVE` 同族的未定标识 |
| 操作 / 焦点 / 运行中 | 独立于三结论的交互色 |
| 技术故障与危险操作 | 专用错误样式，**仅**用于此，绝不用于 `NO_EVIDENCE` |

排版：中性无衬线承载叙述；等宽字体仅用于标识符、状态、参数与哈希。

## 6. 首版范围与非目标

范围与上游 §11 一致，按本文档的功能划分重新组织。

### 6.1 首版包含

**入口与运行**

- 一条命令启动本机控制面与打包好的 Web 控制台；终端用户不需要额外的前端工具链（上游 §5.1、§5.2）。
- 一人一机的本机运行（上游 §3.2、§11）。
- durable Job API 与本机 worker 监管（上游 §11）。
- checkpoint 与重启恢复（上游 §11）。
- 任意时刻提交；提交立即返回 `run_id`；任务独立于浏览器与提交 shell 长时间运行。
- 主机唤醒约束的显式披露。
- 取消、续跑、重放结论。

**研究定义**

- 引导式假设输入与等价的结构化输入，双向同步。
- 冻结的研究规格（上游 §11）。
- 受约束策略 DSL（上游 §11）。
- `us-equity-daily` 与 `crypto-daily` 两个独立市场档案（上游 §5.5、§11）。
- 内容寻址的数据快照；重放失败关闭（上游 §7）。
- **验证方法配置**：验证点登记表结构、硬门槛 / 绑定子校验 / 全轮硬校验 / 诊断项四类、市场档案 ⊕ 协议模板默认、可行性预判、放宽留痕、随协议冻结并计入协议指纹。
- 预检与协议冻结，含验证清单终确认。

**观测与结论**

- 进度总览（预算、试验、检查点、心跳），无假进度、无预测倒计时。
- 试验台账（只读、只增、全部计入多重检验计数）。
- 候选漏斗与淘汰主因，只读，无覆盖控件。
- **验证进度**：逐验证点 `pending` / `running` / `pass` / `fail` / `skipped`（含原因）/ `incomplete`。
- 三结论与唯一主结论 + 主要证据 + 停止原因（上游 §11）。
- 证据与 trial ledger 产物（上游 §11），证据摘要可下钻。
- **策略验证结果**：每个入围与淘汰候选逐验证点结果，结论页与策略详情共用同一组件。
- 带 epistemic stopping 的迭代研究（上游 §11、§6.2）。
- 方法修订复盘；经济性修订（含改验证清单）转人工队列。
- 下一假设建议队列，只建议不执行。

**交接**

- 人工触发的不可变 `.asb` 导出，仅 `FOUND` 可导；血缘含验证清单与放宽项（上游 §8.2、§11）。
- 包内无可执行文件、无凭据；导入不等于授权交易（上游 §8.2.1、§8.4）。
- `.asb` schema 中保留可选的注册表地址字段（上游 §11）。

**次要入口**

- CLI 与本机 Agent Skill（上游 §11）。

### 6.2 首版非目标

**能力上明确不做（产品边界，不是排期问题）**

- 不交易：不持有券商凭据、不连接券商、不提交模拟或实盘订单、不调用 AlphaStrategy 执行接口（上游 §9.4）。
- 不自动晋级：任何候选都不会自动进入模拟盘或实盘；导出是人工动作，导入之后的晋级归 AlphaStrategy（上游 §8.4、§9.4）。
- 不做团队协作：首版没有团队身份、权限与审批流（上游 §11）。
- 不覆盖证据门槛：界面、报告、LLM 评审、agent 叙述都不能改门槛结果；不存在覆盖控件（上游 §9.3）。
- 不执行任意生成代码：候选是 DSL 文档加冻结参数，不是新的代码模块；`.asb` 内不含任何可执行载荷（上游 §8.2.1、§11）。
- 不在同一轮里静默执行新经济假设（上游 §4.3、§6.1）。
- 不承接 AlphaStrategy 的实现工作，也不接收其回传遥测（上游 §8.1、§11）。

**首版不做（未来可能做）**

- MCP 适配器。未来的 MCP 只做短异步操作，且**绝不为一次长时间运行保持调用打开**（上游 §10.4、§11）。
- 官方托管云与远端 worker 实现。本机执行是默认；未来用户自有的云端 worker 必须实现同一套 Job API、运行状态机、worker 协议与产物契约（上游 §5、§11）。用户自有云端 worker 是为无法让主机长时间保持唤醒的场景准备的（上游 §4.1）。
- 桌面壳打包（上游 §10.5、§11）。
- Bundle Registry（上游 §11）。
- 自定义验证点（用户自带检验函数）与产品界面内的可调阈值。前者走登记表的版本升级；后者会打开「调到通过为止」的后门（上游 §6.2）。
- 跨运行 / 跨市场档案的候选排名。跨市场只做可移植性检验，不比较绝对绩效（上游 §5.5）。
- 界面文案的本地化。术语与 CLI、配置、证据文件共享词汇，本地化需要连同这几处一起规划。

## 附录 A：数据契约增量

本节说明为支撑 F4、F10、F13 需要在契约上增加什么。这是**设计意图与语义要求**，字段名与文件布局归运行时规格（§0.3）。

### A.1 冻结的验证清单

验证清单必须与假设同等级地被冻结。上游 §6.1 已把「成功标准」列入冻结集合，本节把它具体化：

- 清单是冻结协议文档（上游 §7 的 `research-spec.yaml`）的一部分，而不是旁挂的可变配置。
- 协议指纹必须覆盖清单内容。改清单即改协议，得到不同的指纹。
- 冻结时一并记录：默认清单的来源与版本（市场档案 + 协议模板）、用户的改动、放宽项与原因。这样才能回答「当时的默认是什么、用户改了什么」。
- 引入清单字段属于 schema 版本升级；既有协议文档必须仍能被校验与重放。

### A.2 运行期的逐验证点状态

运行期需要一份可增量更新、可被界面读取的验证进度：逐验证点的 `pending` / `running` / `pass` / `fail` / `skipped` / `incomplete`、跳过原因、以及当前正在评估的候选。

它是**派生的运行期状态**，不是结论来源；结论仍然只从已封存的门槛证据推导（上游 §7、§9.3）。

`skipped` 必须是一等状态并带原因，不能用「缺席」来表达。这是 §3.10 结论语义的前提：能被表达，才能被降级。

### A.3 每候选的验证结果

上游 §7 规定证据目录保存硬门槛判定的原始输入。为支撑 F13 需要补上：

- 每条结果的 `class`、`scope` 与归属，这样界面才能还原 F4 的分组与缩进。
- `skipped` 状态与原因，以及父门槛的 `incomplete` 状态与导致它的子校验标识。
- 指向原始证据的引用，供下钻。

### A.4 视图载荷

任务详情的视图载荷需要新增三块：冻结的验证清单（含放宽项）、运行期验证进度、每候选验证结果。三者共用同一套验证点标识与释义，保证 F4、F10、F13 三处界面在措辞与顺序上完全一致。

### A.5 导出血缘

`.asb` 的血缘（上游 §8.2 的 `lineage.yaml`）需要记录本轮验证清单与放宽项。下游拿到一个候选包时，应当能回答「这个 `FOUND` 是在什么标准下得到的」，而不只是「它通过了」。

## 附录 B：术语表

| 术语 | 含义 |
| --- | --- |
| 随时提交 | 用户在任何时刻定义并冻结研究任务，提交即得 `run_id`；产品不假设提交时刻 |
| 长时间自主研究 | 任务可跑数小时，独立于浏览器与提交 shell，由 checkpoint 保证可恢复，由预算与停止规则保证可终止 |
| 可靠结论 | 用户回到界面时读到的唯一主结论、主要证据与停止原因，可复现、可审计 |
| 验证点 verification point | 本轮研究中一次可判定的检验；分硬门槛、绑定子校验、全轮硬校验、诊断项 |
| 硬门槛 hard gate | 参与 `FOUND` 判定的顶层验证点；全到齐且全通过才 `FOUND` |
| 绑定子校验 | 挂在某个硬门槛上的硬性检验，让父门槛判定更严 |
| 全轮硬校验 | 对整轮而非某一门槛提问的硬性检验，例如扣费口径与多重检验计数 |
| 诊断项 diagnostic | 被记录与展示但永不决定 `FOUND` 的验证点 |
| 放宽 relaxation | 相对默认清单的削弱：关门槛、降级为诊断、关绑定子校验或可关闭的全轮硬校验 |
| 放宽留痕 | 放宽在配置处、冻结确认处、结论页与 `.asb` 血缘四处留下记录 |
| 可行性预判 | 冻结前对每个验证点给出可执行 / 可能跳过 / 必定跳过 |
| `skipped` | 验证点因前置条件不满足而未能执行；硬门槛被跳过导致 `INCONCLUSIVE` |
| `incomplete` | 门槛自身有结果，但其启用的绑定子校验被跳过，因此不计为通过 |
| 协议冻结 freeze | 把假设、市场档案、数据快照、预算、成功标准与验证清单一并固定 |
| 协议指纹 | 冻结协议内容的哈希，覆盖验证清单；具体字段名归运行时规格 |
| `run_id` | 一次研究运行的标识，提交时立即返回 |
| trial ledger | 试验台账；每个候选、每次实验与每次方法性修订的只增记录，全部计入多重检验计数 |
| `checkpoint` | 可续跑的 worker 状态快照 |
| 候选漏斗 | 候选在各门槛上的淘汰分布与主因 |
| 方法性修订 | 数据、实现细节、成本假设、参数覆盖层面的修订，本轮可执行 |
| 经济性修订 | 经济逻辑、信号机制、市场范围、成功标准（含验证清单）的改变，本轮不可执行 |
| `.asb` | Strategy Candidate Bundle，交给 AlphaStrategy 的不可变数据包 |
| 市场档案 market profile | 交易日历、数据集要求、基准、交易成本假设、流动性规则、存续与可用性检查的集合 |
