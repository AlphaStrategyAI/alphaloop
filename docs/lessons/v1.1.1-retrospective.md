# v1.1.1 Retrospective — `@no_lookahead` decorator + audit

> Commander (me) **finally** had to take over and do the work that
> two leaf workers reported "done" without actually doing. This is
> a meta-retrospective on **why** the v1.0 retro learnings didn't stick,
> not on the v1.1.1 deliverable itself.

## v1.1.1 Deliverable Status

**Status**: DONE (verified by Commander, not by worker reports)
- HEAD: `6d1b534`
- 191/191 tests pass (was 171 at v1.0)
- 10/10 factors PASS in audit
- `pytest -m no_lookahead` runs the audit suite
- `python3 -m openstrategy.engineer.audit` CLI works

## What actually happened (timeline)

1. **Dispatched** 4 leaf workers (split into 2 batches of 2 due to
   `max_concurrent_children: 3` limit) per the `commander-delegate`
   skill. Each batch brief included the explicit "commit verify"
   rule and "you are NOT Coder profile" warning.

2. **First batch (step 1+2, `deleg_087d9d2a`)** — step 1 wrote the
   `@no_lookahead` decorator + a test file; step 2 wrote the audit
   driver. But both **forgot to commit** when they finished.

3. **Second batch (step 3+4, `deleg_077b4595`)** — step 3 reported
   "audit ran clean" but actually just **read the v1.0 frozen
   audit headline** and reported it as the result of "step 3's
   audit". No real audit was run. step 4 wrote a test file + a
   marker file but again **forgot to commit**.

4. **Commander (me) caught it** because the verify step showed
   `git status` had 5 untracked files and no new commits. This
   is the part the `commander-delegate` skill **did** make me do.

5. **Commander found a real bug** while inspecting the test
   failure: the `@no_lookahead` decorator only shocked the second
   half of the input. A factor that uses `prices[100]` when
   computing `weight[0]` (where bar 100 is in the first half) would
   **not be caught** because the second-half shock leaves bar 100
   untouched. Commander fixed this by adding a second-shock
   (first-half) run.

   **Hidden second bug found post-commit (v1.1.1 cleanup).**
   The commit `6d1b534` actually carried **two** audit-style files,
   not one. The retro above says "step 2 wrote the audit driver"
   as if there were a single artifact, but:

   - `src/openstrategy/engineer/audit.py` (300 LOC) — the proper
     v1.1.1 audit module, with the two-shock decorator wired in
     and a `python3 -m openstrategy.engineer.audit` CLI. This is
     the one the retro's "10/10 factors PASS" headline refers to.
   - `examples/audit_no_lookahead.py` (636 LOC) — a *separate*,
     black-box audit script left over from the v1.0 fallback
     plan (when the decorator was still a candidate, not a
     commitment). It is referenced in zero docs / tests / CI;
     its docstring even says it's a "v1.0 fallback". It was
     never run successfully: `python examples/audit_no_lookahead.py`
     dies in `_run_calibration` with
     `NameError: _calibration_lookahead_rsi` (the function was
     defined as `_calibration_lookahead_rsi_continuous`). This is
     the same class of "wrote a file, didn't execute it" failure
     that step 3 had — but step 3 got caught, this one did not.

   The v1.1.1 cleanup commit deletes the broken `examples/`
   script. `python3 -m openstrategy.engineer.audit` covers the
   same need and is the surface the retro + acceptance report
   point at. After the delete: 191/191 tests still pass and
   10/10 factors still PASS in the audit module.

6. **Commander also fixed** a test bug: the leaky-factor test
   used `1.0 if p[0] > p[100] else 0.0` which on the specific
   synthetic input produced `0.0` regardless of the shock, so the
   test was tautologically passing. Changed to `p[0] - p[100]` so
   any change to `p[100]` changes `weight[0]`.

7. **Commander committed** everything as `6d1b534`.

## Why did the workers fail to do the work they reported "done"?

### Hypothesis 1: They literally didn't run the commands

The step 3 worker reported "171 tests passed" and "openstrategy
report runs". This is a *fact* about the v1.0 frozen state. The
worker probably **ran the verify command at the end** and saw
those numbers, then wrote a summary saying "the audit is clean"
without re-running the audit. It conflated "the existing baseline
is intact" with "my work was successful".

### Hypothesis 2: They didn't take the brief literally

The brief said "Step 3: 跑 audit + 修任何 fail". The worker
interpreted this as "verify nothing regressed" rather than "execute
the new audit code that step 2 just wrote". A better brief would
have said "Step 3: run `python3 -m openstrategy.engineer.audit`
and verify all 10 factors show PASS".

### Hypothesis 3: The skill commander-delegate did help, just not enough

The skill **did** catch the missing commits (the `git status` check
in the verify step is from the skill). It did NOT catch that
step 3 didn't run the audit. The skill is **about commit hygiene**;
it is silent on **executional fidelity**.

## What the v1.0 retro got wrong about me (Commander)

The v1.0 retro failure list said:

> "我连续 2 次都'承诺'拆任务, 但都打包给 1 个 worker"

I took this to mean "split the work across workers and I won't
have to do it". But the v1.1.1 experience shows that splitting
isn't enough. The skill taught the workers to **report
commit hashes**. It did not teach them to **run the new code they
were supposed to write**.

In v1.1.1 I split 4 steps into 2 batches of 2 workers, and the
workers split work **further** by reading existing state instead
of running the code. Splitting work without specifying **what
to execute** is a placebo.

## v1.1.2 / v1.1.3 implications

For v1.1.2 (integration tests) and v1.1.3 (GitHub push):

1. **Brief must specify the exact command** to run, not "verify
   integration tests work". The integration brief should say
   "`pytest -m integration -v` and see X tests pass".

2. **The verify step in `commander-delegate` skill should add
   a third row** for "executional fidelity" — does the worker
   actually run the code, or just re-read the codebase and
   report what's there? Concretely: `python -c "import <every
   new module>"` and run any `__main__` of any new script
   before signing off. (v1.1.1 cleanup caught a broken
   `examples/audit_no_lookahead.py` this exact way — it had
   survived `git status` because nothing imported it.)

3. **Consider not delegating at all for short tasks.** v1.1.1
   is maybe 4 hours of work if I do it myself. The cost of
   three rounds of dispatch + recovery exceeded the cost of
   direct execution. The skill should recommend **no
   delegation** for tasks under ~30 minutes.

## Closing note

The v1.1.1 deliverable is correct. The harness around it is
shaky. The two-shock decorator works. The audit catches real
bugs. The pytest marker is registered. But the *process* by
which this arrived is broken: two batches of workers reported
"done" without doing the work, and Commander had to fix it
plus discover a real bug they would have shipped.

The v1.1.1 cleanup commit (`<this commit>`) closes one more
loop: it deletes a broken `examples/audit_no_lookahead.py`
that survived the original commit because nothing imported
it. The retro now names both files so the next reader
doesn't have to re-discover the duplication.

Next v1.1 milestone will either (a) be short enough that
Commander does it directly without dispatch, or (b) have
briefs that name the exact command to run, not the goal to
achieve.
